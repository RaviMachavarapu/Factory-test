## What this means for an instance scaffolded from v3.2.0

This file is the factory's own record. Proposed Changes, item 10 (carried by this PR) fences it out of instances, and an instance's
`docs/BACKLOG.md` (from `templates/BACKLOG.md`) never holds the BL ids below, so a founder reads these lines here, and
Proposed Changes, item 11 has the next release's migration and known-limitations carry them to instances. A *v3.1
instance* is one scaffolded from the v3.1 template. "On `main`, unreleased" means merged to the factory's `main` after
`v3.2.0`: it reaches an instance only with the next template release (3.2.1, planned by 2026-11-15, BL-022), taken on an
`upgrade/<version>` branch.

- **The first release of a python or v3.1 instance is refused (BL-034).** It affects python and v3.1 instances; tauri
  and flutter instances do not carry the demo. Now: hold your first tag. `release-tag.sh` exits 11
  (`previous-untagged`), and you must not run the message's remedy, `/release --tag 0.0.1-demo`: never tag the demo,
  since that records a release your project never made (`docs/releases/3.2.0-known-limitations.md`). The fix is code,
  on a `build/sec-<id>` back-edge or the v3.3 design lane. Which one, and so whether 3.2.1 carries it, is decided at the
  3.2.1 ship; v3.3 has no date. The factory's own re-tag of `v0.0.1-demo` (M7, BL-033) changes nothing in an instance,
  which never holds that tag.
- **Taking the next template release (BL-036).** No upgrade lane exists before v3.3, which is undated. Take 3.2.1 on an
  `upgrade/<version>` branch following `docs/releases/3.2.0-migration.md` §1: `/next` reports the branch as unknown and
  renders no merge command, and the maintainer merges by hand after the verifier's `APPROVE` or a waiver. That first
  upgrade PR is judged by your v3.2.0 `main`'s classifier, so a waiver there takes the legacy `sha:<head>` form, never
  the bound form, which that classifier rejects as `malformed` (`docs/GLOSSARY.md`, Waiver).
- **Waivers name a head only (SEC-006), every instance.** Base-bound waivers are on `main`, unreleased (PR #65, Tasks
  1.1–1.2). Until you take them, re-read a waived PR after any retarget.
- **The python image runs as root (SEC-011), python instances.** The non-root `USER 10001` and the hash-pinned runtime
  lock are on `main`, unreleased (PR #65, Task 1.4); a v3.2.0 image still runs as root with no hashed runtime install.
  A python instance's first ship is also the first real GHCR push (SEC-018; BL-009, BL-010, BL-015): tell the
  maintainer, kpingali123, when yours ships, since those deferrals wait for it and the factory cannot see your
  repository.
- **`signing: apple` instances carry SEC-005.** v3.2.0's `release-sign.sh` signs the entitlements the unsigned bundle
  embedded, not your committed file. It is fixed on `main` by PR #65 (Task 1.3), unreleased, and reaches you with the
  next template release. Until then, compare `codesign -d --entitlements :-` on the signed app with your committed
  entitlements before you publish the draft Release (`docs/releases/3.2.0-known-limitations.md`). A first signed
  instance release also carries SEC-013 (the Apple secrets on argv, BL-016) and SEC-014 (registry caches in the bundle,
  BL-017) unfixed, and is the first real run of the signed path (SEC-019, BL-018): tell the maintainer, kpingali123,
  when yours ships. python instances, the template and `signing: none` bundles are not affected.
- **tauri instances: SEC-001..003 expire on 2026-12-24.** The template's re-pin (Proposed Changes, item 1) never reaches
  an existing instance. Before 2026-12-24, renew SEC-001..003 in your own `/security-review` (`osv-scanner.toml`'s
  `ignoreUntil`, the `src-tauri/audit.toml` comments, your own disposition entries), or upgrade the dependencies, or
  your floor fails on that date (`README.md`, "Known limitation").
- **Open mediums will count toward the cap (BL-002).** No change before v3.3. Once an instance takes v3.3, an open
  medium will need `owner:` and will count toward `medium_cap` (5 in an instance), so a ship PR fails on an ownerless
  open medium or on more than five accepted, deferred or open mediums.
- **The Dependabot exemption (BL-014; SEC-015, dfe-13) applies in every instance.** The classifier is the same: in solo
  mode an exempt Dependabot PR merges with no second review, and a forged commit can move an existing dependency to
  another registry version of the same package. Meanwhile an instance can read each Dependabot PR's diff, or run the
  verifier on it, before merging: the exemption makes the check pass without a marker, it does not forbid a review.
  The decision falls to the next retrospective, run after the next ship PR merges (3.2.1, planned by 2026-11-15).

Everything else in Proposed Changes is the factory's own housekeeping (items 2 and 4–10). Item 1 changes the pins new
instances are scaffolded with. Item 3's constitution wording reaches instances with the template release after
amendment D lands; it aligns the articles' wording with the mechanisms that already run. Item 11 carries this section
to instances.
