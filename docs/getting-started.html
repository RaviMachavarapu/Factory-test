From an idea to a signed release, with you deciding at seven points

This repository turns a one-page idea into a tested, security-reviewed, released product. Claude does the writing and the building. You bring the idea, answer a handful of questions at each stage, run one command from a second terminal, and press merge. This guide shows what the idea must contain and exactly what you will be asked along the way.

Who does what

Three parties work on every product. Knowing which is which makes the rest of this guide short.

You

Own the idea and every decision about scope, risk and shipping. You never read a diff to decide. You confirm plain-English summaries, run the independent review from a second terminal, and merge.

Claude Code

Writes the specification, the architecture, the plan, the tests, the code, the security review and the release notes, one lane at a time, and asks you only at the confirmation points below.

The pipeline

Branches, pull requests and automated gates that refuse to merge work that lacks tests, a security review, or an independent review. One honest limit: in solo mode the independent review is an audit trail, not a lock. You are the repository's admin, so you can merge past a red check, and a free private repository enforces none of it server-side. The record of what was skipped is permanent either way.

The pipeline has two profiles. This guide describes the guided profile, the default for founders: Claude runs each step and pauses for your yes. The engineer profile prints the same steps for you to run yourself.

Before you start

Setup is three commands, run once in a fresh copy of this repository. If you are reading this inside a project that already has its own idea file and branches, setup has run and you can skip to the next chapter. The first command asks four things; the second pushes the result to GitHub; the third makes the review checks required on the main branch, which setup itself never does.

bash scripts/init-project.sh --doctor    # report-only: what is missing on this machine
bash scripts/init-project.sh             # the one-time setup: four prompts, then a local commit on main
git push -u origin main                  # your empty GitHub repository, added as origin first
bash scripts/configure-repo.sh           # requires the gates and verifier checks on main; on a free private
                                         # repository it reports what GitHub refuses to enforce

  1. Your profile

    Press Enter for guided. Choose engineer only if you want to drive the commands yourself.

  2. Your project's name

    A plain product name, such as Habit Tracker. It names the repository's documents and, for a desktop app, the app itself.

  3. What are you building?

    A numbered menu. Each choice fixes the technology stack and what you will be able to hand out at the end.

    ChoiceWhat you getNeeds on your Mac

What you need in place
  • Claude Code installed and signed in, and the GitHub command-line tool gh signed in to the account that owns the repository.
  • An empty GitHub repository for the project. After setup you push to it and run the repository configuration yourself, as above. Public, or private on a paid plan, gets enforced branch protection; a free private repository gets the same checks as advice only.
  • The toolchain for your choice above; the setup check prints each missing piece with the command that installs it.
  • For a desktop app you later hand out: a second Mac to test the download on, and about two hours of CI minutes per release on a free plan.

Writing the idea

Your idea lives in one file, IDEA.md, with five headings. Everything Claude builds traces back to it, so the time you spend here is the highest-leverage time in the whole project. The file is the only place where you write prose; after it, you mostly answer questions.

A complete example: a macOS habit tracker

An example in the spirit of the walk the template's maintainers have planned for this same product. It is small on purpose. A good first idea is one you can describe in five short paragraphs.

# IDEA.md

## Idea
A macOS desktop app where I add a few daily habits, check each one off
today, and see how many days in a row I have kept it up. Single user,
one machine, no account.

## Objective / Done Looks Like
I open the app, see today's list, and check off "Walk 30 minutes". The
streak counter next to it goes from 6 to 7. Tomorrow the checkbox is
clear again and the streak is still 7 until I miss a day. I can hand the
app to a friend as a download and they can do the same on their Mac.

## Target Users
Me, and people like me: one person who wants a light nudge, not a coach.
They have five to ten habits, open the app once or twice a day, and will
abandon it if adding a habit takes more than a few seconds.

## Non-Goals (Explicit Out-of-Scope)
No accounts, no sync between devices, no reminders or notifications, no
sharing, no phone app, no charts beyond the streak number. Not a to-do
list: habits repeat; tasks do not.

## Constraints
Mac desktop app. Data stays on the machine in a plain file I could read
myself. The streak rule must be exactly right: a day counts only when
checked before midnight local time. Free to build and run.

What each section must carry

Idea

One paragraph, in the words you would use to a friend. Say what kind of thing it is (an app, a service, a tool), who uses it, and the one thing it does. Too thin: "A habit app." Enough: the paragraph above.

Objective / Done Looks Like

Describe one concrete moment of use as if it already works, including what you see on screen. This becomes the acceptance test for the first release. Too thin: "Users can track habits." Enough: a before-and-after a tester could reproduce.

Target Users

Who, how often, with what patience. If there are two kinds of user, name both; each becomes a persona in the specification. The details that matter are the ones that change a design decision: how many items, how often they open it, what makes them quit.

Non-Goals

The most valuable section for an AI builder. Everything you exclude here will not be designed, built, tested or reviewed, which keeps the first release small enough to finish. List what a reasonable person might assume you want and you do not.

Constraints

Platform, where data lives, anything that must integrate with an existing system, legal or privacy rules, budget, and any rule that must be exactly right. A rule you mark as critical can be formally proved during the build; name those plainly.

Checklist before you leave this file
  • Someone else could tell, from the Objective alone, whether the first release works.
  • Every exclusion a builder might otherwise assume is written under Non-Goals.
  • You have named where the data lives and who else can see it.
  • Any calculation or rule that must never be wrong is called out, so it can be proved rather than only tested.
  • Any outside service, account or API the product depends on is named, with whether you already have access.
  • The whole file still fits on one screen. If it does not, you have two ideas; keep one for a later lane.

You will not be asked to write the specification, the architecture or the plan. Claude writes those from this file and from your answers, and each is summarised back to you in plain English before it is committed.

The journey: three lanes, one release

Work moves through three kinds of branch, called lanes. Each lane ends in one pull request that the gates and the independent review must approve before you merge it. The command /next in Claude Code always knows which lane you are in and what comes next; in the guided profile it also runs the step for you.

Design lane

From your idea to a plan: a brainstorm you take part in, a specification, the architecture with its threat model, and a build plan split into numbered builds. One pull request.

Build lanes

One per numbered build in the plan. Tests are written before the code, critical rules are proved, and the pull request's own checks are the validation. Usually two to four builds for a first release.

Ship lane

The security review with every finding scored and dispositioned, then the release notes, migration notes and known limitations. One pull request, then the signed tag, then the published release.

The seven moments the pipeline waits for you

In the guided profile these are the only pauses. Each shows you what it names and continues only on your yes.

brainstorm end
A decision: the product scope Claude has drawn from your idea and your answers. Say yes to write the specification, or push back.
design PR
An acknowledgement: the specification summary, which rules will be formally proved, and the main risks. Your handle and the date are written into the documents as the confirmation.
build PR
An acknowledgement: what was built, in your terms, before the build's pull request is pushed.
ship PR
An acknowledgement, then a decision: the severity of every security finding and how each is handled, then go or no-go for the release.
awaiting verifier
Claude prints one command and waits. You run it in a second terminal. See the next chapter.
merge
A decision: Claude shows the merge command and asks before running it. Only an approved pull request ever reaches this point.
unsigned tag
An acknowledgement, only when no signing key exists on the machine: confirm that the release is tagged without a signature, which is recorded in the known limitations.

What you will never be asked

To read code or a diff, to write a test, to choose a library, to score a security finding from scratch, or to decide how a document is formatted. When the pipeline refuses something, Claude tells you what it refused and why, in your terms, and proposes the fix.

The second terminal

Every pull request needs an independent review before it can merge. In solo mode that review is an automated verifier: a separate Claude run, started from outside your working session so it cannot be steered by it, that reads the pull request against the rules and posts an approval or a list of findings. The required check stays red without that approval; as the admin you could merge anyway, and the missing approval would stay on the record.

When Claude reaches the awaiting-verifier point it prints a line like this. You open a second terminal, go to the project, and run it.

export GH_TOKEN="$(gh auth token)"
cd ~/path/to/your-project
git fetch origin
git show refs/remotes/origin/main:scripts/run-verifier.sh | bash -s -- <PR number>
What happens next
  • Approved: paste the output back to Claude. /next moves to the merge point and shows the merge command.
  • Findings: paste them back. Claude folds the fixes in, re-reviews its own changes, pushes, and you run the command once more. One or two rounds is normal; release documents sometimes take more, because every finding there must be settled before the release is frozen.
  • Never copy the command from a CI log page; use the line Claude printed. The printed line always runs the reviewed copy of the script from your main branch.

Run it only after the pull request's own checks have started; if your main branch has moved since the pull request was opened, the script says so and Claude rebases first. Each run uses your Claude subscription, not an API key.

After the release

  • Handing it out. A desktop app without an Apple developer signature ships with generated tester instructions: the download, the "Open Anyway" steps, and how to remove the quarantine mark. With the five Apple signing secrets configured in the repository's release environment, the app is signed and notarized instead.
  • The next idea. Edit IDEA.md or write a new one and start a new design lane. Requirement numbers continue from where the last specification stopped, so everything stays traceable across releases.
  • Security findings you accepted. Each has an owner and an expiry date. The next release's review carries them forward and the gates refuse a release whose accepted findings have lapsed, so they are re-examined on a schedule rather than forgotten.
  • Retrospectives. After each release, /retrospective records what worked, decides every open item in the backlog, and proposes changes. Proposals are applied by their own small pull requests.
  • Template upgrades. A newer version of this template is taken on its own branch following the migration notes of that version; it is the one change that does not fit a lane yet.

Words you will meet

lane
A branch that carries several pipeline phases as one pull request: design, build or ship.
gates
The automated checks that run on every pull request: tests, test-first per commit, coverage, the security floor, formal proofs, document consistency.
verifier
The independent automated review of a pull request, run from a second terminal; its approval is required to merge.
confirmation point
One of the seven moments the guided profile pauses for your yes.
guided proposals
The section in a document where Claude records what it proposed and what you acknowledged, with your handle and the date.
verifiable rule
A requirement tagged to be formally proved with Dafny as well as tested; use it for the rule that must never be wrong.
security floor
The minimum scans every pull request passes: secrets, known-vulnerable dependencies, and the stack's own audit.
disposition
What was decided about each security finding: fixed, accepted with an owner and expiry, or deferred with a trigger. Critical and high findings are never accepted.
patch
A small change that does not warrant a full lane: one pull request, still with the gates and the verifier.
