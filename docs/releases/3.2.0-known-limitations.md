## The release's own controls, as measured

- **The tag, and what trust on first use proves (SEC-007).** `v3.2.0`
  will be the first SSH-signed release tag in this repository's history.
  `/release --tag 3.2.0` (`scripts/release-tag.sh`) creates it after this ship
  PR merges. `v0.0.1-demo`, the only earlier release tag, is annotated and
  not signed, so no earlier signature vouches for a key. The signing anchor
  is trust on first use: commit `7d40ddec750262dae37906c651f28f53c852fa34`
  (Build 1's merge, PR #53), the first first-parent commit of `main` whose
  `.github/allowed_signers` lists a key. That commit lists one key:
  - ED25519, fingerprint `SHA256:9Ik+/iaEifQJ0mLR8vM/x8lbX+pcQ3rG52kG4gzvUy0`;
  - principal `ashwin.pingali@geninspired.com`, namespace `git`.

  The Release body names the anchor. Check that it is this commit.
  Verifying the tag proves only that it was signed by the key this
  repository listed at that commit. Nothing outside the repository vouches
  for the key: on 2026-10-03 the maintainer's GitHub account published no
  SSH signing keys (`gh api users/kpingali123/ssh_signing_keys` was empty).
  An admin controls the repository's history (SEC-009), so treat the key as
  the maintainer's only if you confirm its fingerprint with the maintainer
  some other way. No annotated-tag fallback is recorded for `v3.2.0`. If
  SSH signing is not configured when the tag is made, `release-tag.sh`
  stops instead of making an annotated tag (P6 R17).
- **Verifying the release offline.** The Release body's commands check the
  signature against the anchor's file:

  ```bash
  git show 7d40ddec750262dae37906c651f28f53c852fa34:.github/allowed_signers > allowed_signers
  git -c gpg.ssh.allowedSignersFile=allowed_signers verify-tag v3.2.0
  ```

  That checks less than `signers.py` does at the tag. Do two more checks by
  hand:
  - the `Good "git" signature for <principal>` line must name the tag's
    tagger (`git for-each-ref --format='%(taggeremail)' refs/tags/v3.2.0`);
  - the key must not be listed in `.github/revoked_signers` on `main`.

  For the checks `release.yml` makes, run them yourself, as it does.
  `main`'s `python3 scripts/lib/specflow/attestation.py release-check`,
  with the arguments `release.yml` passes it, re-checks the merged PRs. In a checkout of the tag,
  `bash scripts/verify-release.sh --version 3.2.0 --at-tag` replays the
  release gate.
- **Tag ruleset.** `bash scripts/configure-repo.sh --check-ruleset` printed
  `ruleset: present (id 24361770)` on 2026-10-03 (read-only). It keeps `v*`
  tags from non-admins. A repository admin can still push one through the
  ruleset's admin bypass. `release.yml`'s refusals bind only a tag on a
  reviewed commit, one that carries `main`'s `release.yml` (P6 R31, SEC-009).
  A tag that an admin pushes past the ruleset still verifies offline if the
  anchor's key signed it. Verification proves who signed the tag, not which
  checks ran.
- **Release environment.** `bash scripts/configure-repo.sh --check-environment`
  printed `environment release: present (tag policy v*)` on 2026-10-03
  (read-only).
- **No repository secrets.** The template has no bundle, so `signed` is not
  applicable. `gh secret list` and `gh secret list --env release` were both
  empty on 2026-10-03. The template's Release manifest records
  `signed: null`.
- **GPG-signed tags are refused by `release.yml`** (P6 R27). It verifies SSH
  signatures against `.github/allowed_signers`, and CI holds no GPG keyring,
  so a GPG-signed tag publishes nothing. At PR time, `verify-release.sh` still
  treats a previous release's GPG signature that it cannot check as a WARN,
  because instances may hold GPG-signed tags from before v3.2. Amendment C
  (PR #60, merged 2026-10-03) keeps `release.yml`'s SSH-only rule; whether
  GPG-signed tags return is v3.3's decision (`docs/BACKLOG.md`, BL-008).
- **The one remaining "tag missing" gap.** `/release --tag` creates the tag
  after the ship PR merges. Nothing checks a merged release that was left
  untagged until the next ship PR. That PR's `verify-release.sh` only WARNs
  when the previous release's tag is missing. `release.yml`'s previous-release
  check refuses the next tag in that case, and the PR template's RELEASE
  checkbox is a convention.

## Other residuals

- **The local short-name convention (SEC-016).** CI resolves the base by
  `refs/remotes/origin/<base>`, and since PR #61 the verifier bootstrap pipes
  `refs/remotes/origin/main`'s script for every PR, never the base's. Some reads still use the
  short name `origin/main`, where a tag named `origin/main` could choose the
  ref:
  - `next.sh`'s own advisory git reads;
  - a developer's own gates run (`SPECFLOW_BASE_REF=origin/main`);
  - `release-tag.sh`'s HEAD check, docs comparison and `next:` line.

  `release-tag.sh` fails closed, because it requires `HEAD` to equal the
  remote's `main`. Extending the tag ruleset to cover `refs/tags/origin/**` is
  for the P7 retrospective. Owner: kpingali123; expires 2026-10-12.
- **GHCR is proved only by an instance's ship (SEC-018).** The template ships
  no image, and no python instance has shipped yet. `release.yml`'s image
  path, the GHCR push with the job token and the prune of the superseded
  version have been tested only as workflow text and against stubs. A first
  release reads nothing from GHCR before its push. The image job fails closed
  until the first real push measures it.
- **The python Dockerfile (SEC-010, SEC-011).** The image runs as root. Its
  runtime install is not hash-checked, and its base image is re-pinned by
  hand. P6 R20 froze the Dockerfile. P7 owes `--no-deps` with the hashed
  `requirements.txt` and a non-root `USER`.
- **The macOS release paths are not run in the template's CI.** The signed
  path is exercised only by stub tools (SEC-019). The unsigned bundle path
  runs in the opt-in local first-run cases (`tauri-release`,
  `flutter-release`), not in CI. The first real signed release will be an
  instance's.
- **Cross-image determinism of the source archive is unmeasured** (P6 R18).
  Two pairs of builds have not been compared:
  - this Mac's git 2.54.0 against the ubuntu runner's git;
  - the template's `gates` job on `ubuntu-latest` against `release.yml` and
    `release-build.yml` on `ubuntu-24.04`. These agree only while
    `ubuntu-latest` is 24.04.

  The ship lane measures it once: the laptop's and `release-build`'s
  checksums go in the ship PR, and `build-source`'s in a comment on the merged
  ship PR. CI's build is the record. A laptop that differs is a cross-check
  failure only. Two CI builds that differ fail `release.yml`, and nothing is
  published.
- **Amendment C landed after this review's first commit** (REQ-353, REQ-326;
  PR #60, merged 2026-10-03, onto which this branch was rebased). It says that
  "shipped" means the Release job succeeded from the tag, that the
  laptop-built `dist/` is not the artifact of record, and it rewrites the two
  `art-release-readiness` clauses as settled text. These release records were
  written under the P6 rulings recorded in the spec's P6 entry; the article's
  text now states the same rules.
- **The factory's own release records are fenced from instances (PR #59).**
  At the ship PR's first commit `scripts/factory-only.txt` did not fence
  `docs/security/3.2.0-*` or `docs/releases/3.2.0-*`, so an instance
  initialised from this tree would have inherited these records, which
  kpingali123 owns, with expiries that lapse on 2026-10-12, and
  `tests/governance/test_examples.sh` failed for the tauri and flutter
  instances. PR #59 (merged 2026-10-03) fenced both globs, pinned in
  `test_examples.sh` that no factory release record reaches an instance, and
  made `init-project.sh` give a new instance `medium_cap: 5` with no override
  record. The demo's `0.0.1-demo` records stay. An instance's own SEC
  numbering is unaffected by the factory's.
- **An instance's first release is refused while it holds the demo's
  release notes.** A python instance keeps the canonical demo's
  `docs/releases/0.0.1-demo-notes.md` but never the `v0.0.1-demo` tag. A v3.1
  instance is in the same position. `signers.py`'s previous-release check
  takes `0.0.1-demo` as the previous release, finds no tag and returns
  `previous-untagged`. `release-tag.sh` then exits 11, and `release.yml`
  refuses at the tag too. Only the first release is affected. After it,
  the previous release is the instance's own. The message's remedy
  (`/release --tag 0.0.1-demo`) is wrong for an instance: do not tag the
  demo, because that records a release your project never made. The fix
  is code: leave the inherited demo version out of the previous-release
  walk. `signers.previous` is dfe-12's trust boundary, so the fix never
  takes the patch tier: it goes on a design lane (`design/<slug>`, with a
  spec delta to REQ-383's previous-release rule) or a `build/sec-<id>`
  back-edge under a SEC id raised by the next security review, tracked as
  BL-034 in `docs/BACKLOG.md` (owner kpingali123; a python instance's first
  ship is the deadline, the P7 retrospective decides the schedule). Until a template release carries it, a python or v3.1 instance
  cannot publish its first release through `release-tag.sh` and
  `release.yml`. Hold the first tag until you take that fix. tauri and flutter instances do not
  carry the demo and are not affected.
