# Migration to v3.2.0

These steps move an instance made from v3.1 (the `v0.0.1-demo` template) up
to v3.2.0. A new project needs none of them: run
`bash scripts/init-project.sh`, which does everything below. The new
behaviour is described in `docs/releases/3.2.0-notes.md`.

Do each step on a branch and merge it by PR (`art-branch-as-state`). The one
exception is init's first commit on a new instance.

## 1. Take the template's files and re-run init's new steps

The template's tree carries files that `init-project.sh` removes or rewrites
for an instance. A plain merge brings them in. One of them is the factory's
`.github/allowed_signers`, which lists the factory maintainer's key. The
first commit of your `main` that lists a key becomes your trust-on-first-use
signing anchor. If the factory's key lands there, your instance trusts the
factory maintainer's key, and a tag signed with your own key is refused as
`unlisted`. So do the whole of this step on one branch, and finish it
before that branch's PR merges. Name that branch outside every prefix the
pipeline keys on — `upgrade/v3.2` is recommended — and never `patch/`: a
template upgrade carries constitution amendments, security and release
artifacts and `.github/` workflows, so it falls outside the patch tier as
`review-gate.md` bounds it, and `/next` and the verifier's code mode key
on the `patch/` prefix to apply the patch tier's weaker REQ-citation
fallback. On `upgrade/v3.2`, `/next` treats the branch as unknown and
renders no merge command; the verifier reviews the PR in full+code mode
without that fallback; the maintainer merges by hand after the `APPROVE`
(or a maintainer waiver, REQ-382); and the PR body says it is a template
upgrade. No lane covers a template upgrade yet — BL-036 in the template's
`docs/BACKLOG.md` proposes one:

1. Run `init-project.sh` on a scratch clone of the v3.2.0 template, with your
   instance's flags (stack, profile, path, solo). This scratch instance is
   your reference for what an instance keeps.
2. Merge the v3.2.0 template's tree into your instance on the upgrade
   branch.
3. Before you push, replace `.github/allowed_signers` and
   `.github/revoked_signers` with the scratch instance's comment-only files.
   No factory key may reach a commit of your `main`. Your own key goes in
   by its own PR (step 4).
4. Delete what init deletes:
   - every path that matches a glob in `scripts/factory-only.txt` (the
     factory's own specs, ADR-003, architecture documents, plans, reviews,
     proofs and one unit test), except a path that the `CLAUDE.md`
     "Canonical Example" manifest lists, then `scripts/factory-only.txt`
     itself;
   - `scripts/template-pack.yml` and `scripts/release-template.sh`;
   - `.github/workflows/app-stacks.yml` and `stacks/`;
   - the factory's own release records, `docs/security/3.2.0-*.md` and
     `docs/releases/3.2.0-*.md`;
   - the canonical examples of other stacks, with their `CLAUDE.md`
     manifest subsections (`scripts/lib/specflow/examples.py`).

   Then compare your tree with the scratch instance's. Anything the scratch
   instance lacks, and your project did not add, is template-only and goes.
5. In `.github/workflows/ci.yml`, remove every
   `# >>> specflow:template-only` … `# <<< specflow:template-only` block.
   Then set the `runs-on:` line marked `# specflow:runs-on` and the
   `python-version:` line marked `# specflow:python-version` to the scratch
   instance's values, which come from your pack. Compare
   `.github/workflows/verifier.yml`, `.github/PULL_REQUEST_TEMPLATE.md` and
   `.claude/` with the scratch instance's too.

Then add the files that v3.2 init writes and v3.1 did not have, copying them
from the scratch instance:

- `.specflow.yml` with the keys `profile`, `path`, `stack`, `solo`,
  `coverage_min` and `signing` (REQ-301). Run
  `python3 scripts/lib/specflow/config.py --root . validate` to check it.
- `.specflow/pack.yml` and your stack's pack files (REQ-303).
- `scripts/release-<stack>.sh`, the release hook that follows
  `scripts/release-stack.sh.template`'s contract (`VERSION`, `DIST_DIR`,
  `RELEASE_PARTS`, `RELEASE_COMMIT`). It writes manifest schema 2 from the
  committed tree (REQ-305, REQ-384).
- `.github/allowed_signers` and `.github/revoked_signers`, comment-only
  (above). An instance trusts none of the factory's keys. Your release tag
  signers go in by PR (step 4). List a key in `revoked_signers` to revoke
  it.
- `.github/actions/release/`, your stack's release action, which `release.yml`
  runs.
- `.github/workflows/release.yml` and `.github/workflows/release-build.yml`.
- **python only:** the pack's `Dockerfile`, and `scripts/deploy-local.sh`.
  `deploy-local.sh` is the local example of the four-part deploy contract:
  migrate, deploy, smoke and rollback (REQ-351).
- **tauri and flutter only:**
  - `docs/releases/tester-instructions.md`, the pack's template for unsigned
    bundles;
  - `docs/releases/store-checklist.md`, the macOS distribution checklist.

Run `bash scripts/run-quality-gates.sh` on the branch before you open its PR.

## 2. Set `signing:` in `.specflow.yml` (tauri and flutter)

`signing: none` is the default. It ships an unsigned bundle with tester
instructions in the Release body. `signing: apple` signs and notarizes, and it
needs all five secrets in the `release` environment:

- `APPLE_CERTIFICATE_P12`
- `APPLE_CERTIFICATE_PASSWORD`
- `APPLE_ID`
- `APPLE_TEAM_ID`
- `APPLE_APP_PASSWORD`

If one is missing, the release fails `signing-probe` and publishes nothing.
Write the key with:

```bash
python3 scripts/lib/specflow/config.py --root . write signing=none   # or signing=apple
```

`/release` writes it for you on the ship PR when the secrets it finds differ
from the setting (REQ-354). Python instances leave `signing: none`, because
they build no bundle.

## 3. Re-run `configure-repo.sh`

```bash
bash scripts/configure-repo.sh
```

This updates the repository's settings for v3.2:

- **Required checks.** It replaces the v3.1 required checks with the two
  stable names `gates` and `verifier`, and requests zero approvals (solo) or
  one (team) (REQ-312).
- **Tag ruleset.** It creates the `release tags` ruleset, which keeps `v*` tags
  from non-admins (P6 R31).
- **Release environment.** It creates the `release` environment, whose tag
  policy is `v*`. The Apple secrets of an app stack live there and nowhere
  else (P6 R32).
- **Rebase-merge.** It turns rebase-merge off, leaving squash and merge
  commits. The tag-time re-check reads a rebase merge's earlier commits as
  direct pushes (P6 R28).

Check the result read-only:

```bash
bash scripts/configure-repo.sh --check-ruleset
bash scripts/configure-repo.sh --check-environment
```

A GitHub Free private repository refuses protection, rulesets and
environments with HTTP 403. `configure-repo.sh` says so in plain English, and
your release's known-limitations must record the state (`/release` does
this).

## 4. Add your signing key to `.github/allowed_signers` by PR

Each line is one key:

```
<your git user.email> namespaces="git" <key type> <base64 public key>
```

Spell the email exactly as `git config user.email` gives it, because the tag's
tagger is bound to the key's principal and the match is case-sensitive. Add
public keys only.

Merge the line by PR. A key is trusted from the release after the first one
tagged on a commit that lists it. When no earlier release tag in your history
is SSH-signed, the first release is checked on trust on first use: the anchor
is the first commit of `main` that lists a key (REQ-383). That is why step 1
keeps the factory's key off your `main`. If it ever landed there, that
commit would be your anchor, and a tag signed with your own key would be
refused as `unlisted`.

## 5. Configure SSH signing on the machine that tags

```bash
git config --local gpg.format ssh
git config --local user.signingkey ~/.ssh/<your key>.pub
git config --local gpg.ssh.allowedSignersFile .github/allowed_signers
```

`release.yml` accepts SSH signatures only. A GPG-signed tag is refused and
nothing is published (P6 R27). When this machine has only a GPG signer,
`release-tag.sh` stops with exit 5 and the setup steps, and does not tag.

## 6. Make the maintainer's organisation membership public (organisation repositories)

Under the workflow's `GITHUB_TOKEN`, a member whose organisation membership is
private reads as `COLLABORATOR`. That member's waivers are then refused at the
tag (`waiver-not-maintainer`).

## 7. Tag releases with `/release --tag` after the ship PR merges

The ship PR (`ship/<version>`) carries the security and release documents
only. `/release <version>` writes the documents, and `/next` takes you there.

Once the ship PR has merged, run:

```bash
export GH_TOKEN="$(gh auth token --user <the account that can push to main>)"   # only with several gh accounts
```

Then run `/release --tag <version>`, which runs `scripts/release-tag.sh
<version>`. The script:

1. checks the previous release;
2. runs the tag-time re-check over every PR merged since it;
3. signs the merge commit with SSH and checks the signature against
   `.github/allowed_signers` at the anchor;
4. pushes the tag.

The push runs `release.yml`, which publishes the GitHub Release. Do not run
`git tag` by hand. `/release`'s "Tag the release" section lists every exit
code and what to do about it.

**A python or v3.1 instance's first release is refused (exit 11).** Your
instance holds the demo's `docs/releases/0.0.1-demo-notes.md` but not the
`v0.0.1-demo` tag. The previous-release check therefore reports
`previous-untagged`, and `release.yml` refuses at the tag too. Do not follow
the message's advice to tag `0.0.1-demo`, because that records a release
your project never made. Hold your first tag until you take the template's
fix, which is recorded in `docs/releases/3.2.0-known-limitations.md` and
tracked as BL-034 in the template's `docs/BACKLOG.md` (owner kpingali123).
Later releases are not affected.

## 8. Bring existing documents up to the v3.2 formats

- **Plans.** Add `implements: [REQ-NNN, …]` to the frontmatter of every plan
  dated 2026-09-25 or later (REQ-380).
- **Security reviews and dispositions.**
  - Use the block schema `specflow-security/1`
    (`schemas/security-disposition-template.md`).
  - Give every finding a CVSS v4.0 `cvss_vector:` that uses the base metrics
    only. Its band is its severity.
  - A tagged review or disposition changes only under
    `docs/security/README.md`'s schema-migration exception.
- **Tests.** Add a `# Covers: REQ-NNN` line (or `// Covers:`) to tests, so
  every claimed REQ is cited (REQ-323).
- **Suppressions.** Make every suppression cite a live `SEC-NNN` (REQ-388).

Run the gates and fix what they report before the next ship PR:

```bash
bash scripts/run-quality-gates.sh
```

The security floor needs gitleaks and osv-scanner, and the stack's own audits
need their tools. A missing tool is a hard failure that prints the exact
install line.
