## What an instance scaffolded from v3.2.0 must know

Each item below says what to do now, the trigger and date, and how the
change arrives. They come from the v3.2 retrospective's section for
instances, which is fenced from instances, so this file carries them.

- **BL-034: the first release of a python or v3.1 instance is refused.**
  - *Now:* hold your first tag. `release-tag.sh` exits 11
    (`previous-untagged`), and `release.yml` refuses at the tag too. Do
    not run the message's remedy, `/release --tag 0.0.1-demo`. Never tag
    the demo: that records a release your project never made.
  - *Why:* your instance holds the demo's
    `docs/releases/0.0.1-demo-notes.md`, but never its tag.
  - *Who is not affected:* tauri and flutter instances do not carry the
    demo.
  - *Trigger and date:* the fix is code in `signers.previous`, which is
    dfe-12's trust boundary, so it never takes the patch tier. It needs a
    `build/sec-<id>` back-edge or the v3.3 design lane. 3.2.1 does not
    carry it, because this release's security review raised no SEC id for
    it. That makes the v3.3 design lane the route, and v3.3 has no date.
    The deadline the retrospective set stands: before any python or v3.1
    instance's first ship.
  - *Interim path:* none that the factory has tested. Deleting only the
    demo's release records fails `tests/governance/test_examples.sh`,
    because `CLAUDE.md`'s Canonical Example manifest lists them. One of
    BL-034's proposed fixes is that init strip the demo's release records.
    The nearest an instance can do by hand is to remove the whole
    `demo_greeting` example (its manifest subsection and every path it
    lists, as init does for another stack's example). That is untested in
    an instance: if you try it, do it by your own reviewed PR and tell the
    maintainer. Do not publish a
    Release by hand outside `release.yml`: that skips the tag-time
    re-check.
  - *Take 3.2.1 now or wait?* Take it now. Its waiver fix (SEC-006), the
    spec-frontmatter checks and the gate changes apply to every PR you
    open. Its image fixes (SEC-011) apply at your first ship. The BL-034
    fix will come as a later release, taken the same way.
  - *How it arrives:* in the template release that carries the fix, taken
    on an `upgrade/<version>` branch. If your python instance is ready to
    ship before then, tell the maintainer, kpingali123. The factory cannot
    see your repository, and a known instance ship is what would justify a
    back-edge.
- **BL-036: taking a template release is done by hand.**
  - *Now:* take 3.2.1 on `upgrade/v3.2.1` as
    `docs/releases/3.2.1-migration.md` says.
    - Apply the template's diff from v3.2.0 to v3.2.1 three-way; do not
      merge the tag, since an init-made instance shares no history with
      the template. 3.2.0's §1 step 4 also deleted too much.
    - `/next` reports the branch as unknown, and you merge by hand after
      the verifier's `APPROVE` or a waiver.
    - Any waiver on that first upgrade PR takes the legacy `sha:<head>`
      form. Your v3.2.0 classifier rejects the bound form as `malformed`.
  - *Trigger and date:* an upgrade lane waits for the v3.3 spec, which has
    no date.
  - *How it arrives:* with v3.3.
- **SEC-005: `signing: apple` instances.**
  - *Now:* after taking 3.2.1, `release-sign.sh` signs with your committed
    entitlements only, and stops (exit 1) if the bundle embedded a key
    your file lacks. Until you take 3.2.1, compare
    `codesign -d --entitlements :-` on the signed app with your committed
    entitlements before you publish the draft Release.
  - *Trigger and date:* fixed in this release.
  - *How it arrives:* through the migration. `scripts/release-sign.sh` and
    `.github/actions/release/` (§1 step 6).
  - *Who is not affected:* python instances, the template and
    `signing: none` bundles.
- **SEC-006: waivers, every instance.**
  - *Now:* until you take 3.2.1, re-read a waived PR after any retarget.
    After it, post bound waivers (`sha:<head> base:<base>`).
  - *Trigger and date:* fixed in this release.
  - *How it arrives:* through the migration (`attestation.py`,
    `run-verifier.sh`, `review-gate.md`).
- **SEC-011: python instances.**
  - *Now:* a v3.2.0 image runs as root, with no hashed runtime install.
    After taking 3.2.1, the image runs as `USER 10001`. Your runtime
    dependencies must then be listed in `requirements-runtime.in` and
    locked with hashes, or `pip check` fails the image build (migration

  - *Trigger and date:* fixed in this release.
  - *How it arrives:* through the migration (`Dockerfile`,
    `requirements-runtime.*`, `.specflow/pack.yml`).
  - *Another first:* a python instance's first ship is also the first real
    GHCR push (SEC-018; BL-009, BL-010, BL-015). Tell the maintainer when
    yours ships.
- **tauri instances: the skeleton's SEC-001 and SEC-002 expire on
  2026-12-24.**
  - *Now:* before 2026-12-24, renew them in your own `/security-review`,
    or upgrade the dependencies, or your floor fails on that date. To
    renew, bump `ignoreUntil` in `osv-scanner.toml` and in the trailing

  - *Now:* nothing changes in 3.2.1.

  - *What changes then:* an open medium will need `owner:` and will count

  - *How it arrives:* with the template release that carries v3.3.
- **BL-014: the Dependabot exemption (SEC-015, dfe-13) applies in every
  instance.**

    second review. A forged commit can move an existing dependency to
    another registry version of the same package.
  - *Now:* read each Dependabot PR's diff, or run the verifier on it,
    before merging. The exemption makes the check pass without a marker;
    it does not forbid a review.
  - *Trigger and date:* the next retrospective, run after this ship PR
    merges. Its input is the count of Dependabot PRs exempted since
    2026-10-03.
  - *How it arrives:* if the exemption is dropped, in a later template
    release.

## The release's own controls, as measured

- **The tag.** `v3.2.1` will be SSH-signed by `/release --tag 3.2.1`
  (`scripts/release-tag.sh`), on this ship PR's merge commit, after the
  merge.
  - **The anchor.** It is `v3.2.0`, the newest earlier SSH-signed release
    tag. `v3.2.1` is therefore checked against `.github/allowed_signers`
    as committed at `v3.2.0` (commit
    `9f6c6856ab4eff22509dbd8491255f768098ec52`).
  - **The key.** That file lists one key: ED25519, fingerprint
    `SHA256:9Ik+/iaEifQJ0mLR8vM/x8lbX+pcQ3rG52kG4gzvUy0`, principal
    `ashwin.pingali@geninspired.com`, namespace `git` — the maintainer's own
    address (kpingali123 on GitHub): the merger, the tagger and the signer are
    the same person.
    `.github/allowed_signers` and `.github/revoked_signers` are unchanged
    since `v3.2.0`.
  - **The previous tag.** On 2026-10-04,
    `git -c gpg.ssh.allowedSignersFile=<v3.2.0's file> verify-tag v3.2.0`
    printed a `Good "git" signature` line for
    `ashwin.pingali@geninspired.com`, naming the ED25519 fingerprint above.
    `verify-release.sh` checks `v3.2.0` the same way on this PR.
  - **What trust on first use proves (SEC-007).** `v3.2.0`'s own anchor was
    trust on first use (commit `7d40ddec750262dae37906c651f28f53c852fa34`),
    so nothing outside the repository vouches for the key. Confirm its
    fingerprint with the maintainer some other way.
  - **No fallback.** No annotated-tag fallback is recorded for `v3.2.1`.
    The machine that wrote this file reports `signing-kind` `ssh`. If SSH
    signing is not configured when the tag is made, `release-tag.sh` stops
    instead of making an annotated tag.
  - **Before tagging.** P7 plan D17's pre-ship check: run
    `scripts/release-tag.sh 3.2.1 --dry-run`. It runs `release-check` with
    the maintainer's token. The tag-push timeline read under
    `release.yml`'s `GITHUB_TOKEN` is measured only by the first
    `release.yml` run itself. It fails closed (`waiver-timeline-unknown`),
    and a bound waiver recovers it.
- **Verifying the release offline.**

  ```bash
  git show v3.2.0:.github/allowed_signers > allowed_signers
  git -c gpg.ssh.allowedSignersFile=allowed_signers verify-tag v3.2.1
  ```

  This checks less than `signers.py` does at the tag. Also check two things
  by hand:
  - the `Good "git" signature for <principal>` line names the tag's tagger;
  - the key is not listed in `.github/revoked_signers` on `main`.

- **Release environment.**
  `bash scripts/configure-repo.sh --check-environment` printed
  `environment release: present (tag policy v*)` on 2026-10-04 (read-only,

- **No bundle, no secrets.** The template has no bundle, so its Release

- **GPG-signed tags are refused by `release.yml`** (P6 R27). Whether they
