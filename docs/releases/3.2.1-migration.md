# Migration to v3.2.1

These steps move an instance scaffolded from v3.2.0 up to v3.2.1. A new
project needs none of them: `bash scripts/init-project.sh` on the v3.2.1
template does everything below. An instance still on v3.1 takes
`docs/releases/3.2.0-migration.md` first, then this file. What changed is in
`docs/releases/3.2.1-notes.md`.

Nothing here is breaking. Three changes ask something of your own files
(the notes' Breaking section): the spec-frontmatter checks, a python
instance's runtime lock, and `signing: apple`'s committed entitlements.

## How 3.2.1 reaches you

The template does not push anything to an instance. You take a release by
applying the template's changes between two tagged releases to your
repository, by hand, on one branch, by PR (§1):

- **There is no upgrade lane yet.** BL-036 in the template's
  `docs/BACKLOG.md` proposes one. The v3.2 retrospective deferred it to
  the v3.3 spec, which has no date.
- **Use a branch named `upgrade/v3.2.1`.** Do not name it `patch/<slug>`.
  An upgrade carries constitution wording, `.github/` workflows and gate
  code, so it is outside the patch tier.
- **What `/next` and the verifier do with it:**
  - `/next` reports the branch as unknown and renders no merge command.
  - The verifier reviews the PR in full and code mode.
  - You merge it by hand, after the verifier's `APPROVE` or a maintainer
    waiver. Say in the PR body that it is a template upgrade.
- **A waiver is not a step of the upgrade.** The verifier's `APPROVE` is
  the normal route. A waiver is only for a maintainer who decides to merge
  past a `REQUEST_CHANGES`. If you do waive this first upgrade PR, use the
  legacy form: `<!-- specflow-verifier:waive sha:<40-hex head> -->`,
  followed by a rationale of at least 20 characters. The PR is judged by
  your v3.2.0 `main`'s classifier, which rejects the new bound form
  (`sha:<head> base:<base>`) as `malformed`. Once 3.2.1 is on your `main`,
  post bound waivers (`.claude/rules/review-gate.md`, step 4). A waiver
  does not re-run the check by itself: after posting one, re-run the
  `verifier` workflow (`gh run rerun <run-id>`) or edit the PR body. In
  solo mode the maintainer who posts it is you.

## 1. Apply the template's changes from v3.2.0 to v3.2.1

**Your history is not the template's.** `init-project.sh` runs `git init`
and makes its own first commit, so an instance made by init never shares
history with the template. A `git merge` of the template's tag would need
`--allow-unrelated-histories` and would turn every file present on both
sides into a conflict. Do not merge. Apply the template's own diff between
the two releases instead. It brings only what changed in 3.2.1, and git
merges each change into your copy of the file.

`docs/releases/3.2.0-migration.md` §1 step 4 also said to delete every path
that matches a glob in `scripts/factory-only.txt`. Read literally, that
deletes your own files (your `docs/reviews/*.md`, and since v3.2.1 your own
dated `docs/retrospectives/<date>-*.md`). The diff below never adds the
factory's records, so there is nothing of that kind to delete.

1. **Make a scratch reference instance.** Clone the v3.2.1 template
   somewhere else and run `init-project.sh` there with exactly your
   instance's settings: `--name <your project name>` (the package name is
   derived from it), `--stack`, `--profile`, `--path` and `--solo`. Then
   check that the substitution matches yours: in a python scratch,
   `grep -n '__' Dockerfile scripts/deploy-local.sh` prints nothing and
   `Dockerfile`'s `CMD` names your package. This scratch instance is your
   reference for what an instance holds at v3.2.1.
2. **Fetch the two template releases into a private namespace.** On
   `upgrade/v3.2.1` in your instance:

   ```bash
   git remote add template <the template repository's URL>   # once, e.g. https://github.com/Apps-Consultants/factory.git
   git fetch --no-tags template refs/tags/v3.2.0:refs/template/v3.2.0 refs/tags/v3.2.1:refs/template/v3.2.1
   ```

   `refs/template/` keeps the factory's tags out of your `refs/tags/`. A
   factory tag pushed to your repository would start your own
   `release.yml`.
3. **Apply the diff, three-way.** Leave out the paths that are the
   factory's own, or that come from your pack (step 6), or that you keep:

   ```bash
   git diff --binary refs/template/v3.2.0 refs/template/v3.2.1 -- . \
     ':(exclude)stacks' ':(exclude)docs/releases' ':(exclude)docs/security/3.2.1-*' \
     ':(exclude)docs/security/RUBRIC.md' ':(exclude)docs/BACKLOG.md' \
     ':(exclude)docs/retrospectives' ':(exclude)docs/examples' \
     ':(exclude)docs/specs' ':(exclude)docs/plans' ':(exclude)docs/architecture' \
     ':(exclude)scripts/factory-only.txt' \
     ':(exclude).github/allowed_signers' ':(exclude).github/revoked_signers' \
     > ../v3.2.1.patch
   git apply --3way ../v3.2.1.patch
   ```

   Under `docs/specs`, `docs/plans` and `docs/architecture` the template
   changed only its own documents between v3.2.0 and v3.2.1, so excluding
   those directories loses nothing of yours; its other changes under
   `docs/` (the retrospective, the example tree, the backlog) are excluded
   above too, and the rest of the diff (`README.md`, `schemas/`,
   `verification/README.md`, the scripts and tests) is what the patch
   applies. `RUBRIC.md`, `BACKLOG.md` and
   the signer files stay yours: the template's `medium_cap: 8` and its
   override records are the factory's alone, and no factory key may reach
   a commit of your `main` (`docs/releases/3.2.0-migration.md` §1 and §4).
   If `git apply` stops on a path your instance does not have, add
   `':(exclude)<path>'` for it and run both commands again (it applies
   nothing when it stops).
4. **Resolve the conflicts against the scratch instance.**
   `git diff --name-only --diff-filter=U` lists them.
   - **`.github/workflows/ci.yml`** conflicted in the python instance
     this recipe was tried on (scaffolded from v3.2.0, measured
     2026-10-04), and will in any instance: the template changed lines
     inside the `# >>> specflow:template-only` block that init removed. Taking your
     side whole loses the new `concurrency:` group and the Dafny 4.11.0
     pin. If you never edited `ci.yml`, copy the scratch instance's file
     whole. Otherwise keep your edits and take every other line from the
     scratch's copy, which has the template-only blocks removed and your
     `# specflow:runs-on` and `# specflow:python-version` values set.
   - **`CLAUDE.md`** may apply cleanly and still be wrong: the diff adds
     the `### habit_tracker (stack: tauri)` subsection to the Canonical
     Example manifest. In a python or flutter instance remove that
     subsection (`examples.py`'s `strip`, as init does), or the examples
     test looks for its README. In a tauri instance keep it and add
     the README:
     `git checkout refs/template/v3.2.1 -- docs/examples/habit-tracker/README.md`.
   - Any other conflict: keep your own text, and take the template's new
     lines that the scratch instance also has.
5. **Check what was added.** `git diff --cached --name-only --diff-filter=A HEAD`
   lists the new paths (from v3.2.0 to v3.2.1: `docs/getting-started.html`,
   `scripts/lib/specflow/push_guard.py`, `scripts/run-instance-tests.sh`
   and new governance tests and fixtures). `git rm` any that the scratch
   instance lacks. Delete nothing else.
6. **Copy your pack's files from the scratch instance.** They come from
   `stacks/`, which the diff leaves out:
   - `.specflow/pack.yml`. The python pack now lists
     `requirements-runtime.txt` among its lockfiles and pins ruff 0.16.10;
     the tauri and flutter packs carry new toolchain pins.
   - `.github/actions/toolchain/action.yml` and
     `.github/actions/release/`, the pinned toolchain and release actions.
   - **python only:**
     - `Dockerfile`: the non-root `USER 10001`, the hash-pinned runtime
       install and the new base digest. Copy it only from a scratch made
       with your own `--name` (step 1), or `CMD` runs another module.
     - `scripts/deploy-local.sh`: `rollback` with nothing running now
       names `deploy <X.Y.Z>`.
     - `requirements-runtime.in` and `requirements-runtime.txt`, at the
       root, only if you have none. The scratch's are the empty skeleton
       lock; step 7 replaces them with yours.
     - Your dev `requirements.in`: raise the ruff line to
       `ruff>=0.16.10,<0.17`, as the scratch has it, and re-lock
       `requirements.txt` with the command in its header. Keep your own
       entries.
   - **tauri and flutter only:** `docs/releases/store-checklist.md`. It
     now names the refusal of an entitlement key with a different value,
     and flutter's notarizes a zip, staples the `.app` and zips it again.
7. **python only: list your runtime dependencies.** The image now
   installs `requirements-runtime.txt` with `--require-hashes --no-deps`,
   then your wheel with `--no-deps`, then runs `pip check`. A dependency
   your package imports at run time must therefore be listed in
   `requirements-runtime.in`, or `pip check` fails the image build. Then
   regenerate the lock:

   ```bash
   uv pip compile --generate-hashes --universal --python-version 3.12 requirements-runtime.in -o requirements-runtime.txt
   ```

   Every dependency must ship a wheel for linux/amd64 and arm64
   (`--only-binary :all:`). `release-image.sh` refuses a release commit
   without the lock.
8. **Compare with the scratch instance, then run the gates.**
   `diff -rq -x .git <scratch> .` should name only your own code,
   documents and lockfiles. Then run `bash scripts/run-quality-gates.sh`
   on the branch, commit, and open the PR.

## 2. The ask-before-merge hook, and what it asks

The upgrade brings in `.claude/settings.json`'s `permissions.ask` rules and
the PreToolUse hook `scripts/lib/specflow/push_guard.py` (BL-001):

- **When it asks.** In a Claude Code session, the session asks you
  before it runs:
  - `gh pr merge`;
  - a `git push` whose destination is `main`, whatever form the refspec
    takes (`HEAD:main`, `+main`, `--all`, or a push with no refspec
    from `main`).
- **What it is not.** It asks; it never denies. It is a convenience, not a
  control:
  - any PR can edit project hooks;
  - it does not resolve a git alias, a script that pushes, or
    `gh api` merges;
  - branch protection on `main` is unchanged.

  In guided mode a merge costs two confirmations: `/next`'s own yes at
  its `merge` point, then this ask prompt (`.claude/commands/next.md`
  calls the prompt a second confirmation, never a replacement). In a
  non-interactive permission mode the ask may be denied or skipped; run
  `gh pr merge` by hand in that case.
- **If you had your own hooks.** If your `.claude/settings.json` already
  has its own hooks or permissions, merge the two by hand, and keep
  yours.

Nothing to configure. If you do not want it, remove the `ask` entries and
the PreToolUse hook from your `.claude/settings.json` by your own PR.

`scripts/run-instance-tests.sh` also arrives, as it does in a new
instance. It is for the template source: in an instance it refuses with
exit 2 and says so, since your own gates already run your governance
tests.

## 3. The constitution's amendment D: what changed for a reader

Twelve articles still. No slug changes, so your citations stay valid. Each
"How to apply" now says exactly what the mechanism does:

- **`art-naming-tagging`.** The task-id form (`Task N.M`, `TASK-NNN`) is
  convention, not checked. The docs-wide slug check skips two kinds of
  document:
  - archived reviews (`docs/reviews/archive-*`);
  - documents with a `status: superseded` line in their first 20 lines.
- **`art-secrets-hygiene`.** Sessions are denied reads of `.env` and
  `.env.*`. The verifier is denied every `.env*` name.
- **`art-review-gate`.** A change to a source file under your pack's
  `source_roots` (not only `src/`) goes through a PR.
- **`art-threat-driven-security`.** `check-suppressions.sh` is run by
  `tests/governance/test_suppressions.sh` (gates section 3).
- **`art-formal-verification`.** The contract-extraction step is
  convention until v3.3. No REQ carries `[verifiable]` until then.

`.claude/rules/review-gate.md`'s patch tier also admits a rubric-only
reduction of `medium_cap` to the default (5). A raise still needs its own
reviewed PR.

## 4. The pin bump: what to re-run

- **The new pins live in your pack's files** (§1 step 6). The template's
  pins (Dafny 4.11.0, Rust 1.99.0, Node 24.21.0, Flutter 3.47.6,
  `@tauri-apps/cli` 2.12.1, ruff 0.16.10, `actions/setup-node` v7.0.0)
  come from those files. Once you copy them, your CI installs the new
  versions.
- **Dafny.** If you run Dafny locally, install 4.11.0
  (`bash scripts/install-pinned-tool.sh dafny --dest <dir>`). Since 4.10,
  the asset names are `x64-ubuntu-22.04` and `arm64-macos-13`.
- **Your own lockfiles are not regenerated by the upgrade.** These are
  `package-lock.json` and `src-tauri/Cargo.lock`, `pubspec.lock`, and
  `requirements.txt`. Regenerate them yourself if you want the newer
  transitive versions, then run the gates. The floor's osv-scanner reads
  them.
- **tauri instances: renew SEC-001 and SEC-002 before 2026-12-24.** Your
  copies of the skeleton's security records still expire then. On that
  date, the floor fails. The template renewed its own copies to
  2027-03-24, but that never reaches an existing instance. Your options:
  - in your own `/security-review`, bump `ignoreUntil` in
    `osv-scanner.toml` and in the trailing comments of
    `src-tauri/audit.toml`, and add entries under your own version whose
    expiry is no earlier than the new date;
  - or regenerate `src-tauri/Cargo.lock` as the template did. The
    template's regeneration removed the `unic-*` crates, which fixed
    SEC-003.
- **Re-check the result:**

  ```bash
  bash scripts/run-security-floor.sh
  bash scripts/run-quality-gates.sh
  ```

## 5. After the upgrade merges

- **Re-run `bash scripts/configure-repo.sh --check-ruleset` and
  `--check-environment`.** Nothing changed in 3.2.1, but your next
  release's known-limitations records their state.
- **A python or v3.1 instance's first release is still refused (BL-034).**
  3.2.1 does not carry the fix, and there is no tested workaround. Take
  3.2.1 anyway (its waiver and gate fixes apply to every PR), and hold
  your first tag until the release that carries the fix. Do not run the
  message's remedy, `/release --tag 0.0.1-demo`. The known-limitations'
  BL-034 item says why, and what to tell the maintainer.
- **Keep the maintainer's organisation membership public**
  (`docs/releases/3.2.0-migration.md` §6).
