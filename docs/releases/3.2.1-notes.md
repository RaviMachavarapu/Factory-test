# v3.2.1 Release Notes

SpecFlow Factory v3.2.1 is a patch release of v3.2. It carries plan P7's two
builds, the fixes and documentation patches that followed the v3.2
retrospective, and the pinned-download bump. It adds no new pipeline phase
and changes no gate a v3.2.0 instance already passes. It is the factory's
second release on the lanes path. The `ship/3.2.1` branch was started by
hand, because `/next` derives the next version as 3.3.0 (P7 plan R5,
BL-022). The `date:` above is the reproducible build's epoch (P6 R18), not
the tag's date.

These notes are for someone starting a project from the template, or
moving an instance up from v3.2.0. What an existing instance does is in
`docs/releases/3.2.1-migration.md`. What is still open, and what an
instance must do about it before a given date, is in
`docs/releases/3.2.1-known-limitations.md`.

Every pull request merged to `main` since `v3.2.0` is in this release, in
merge order: #66, #64, #65, #68, #69, #70, #71, #72, #73, #74, #75, #76.
PR #67 was a probe and was closed without merging.

## Added

**Waivers can bind a base (P7 Build 1, PR #65; REQ-382, REQ-311)**

- A maintainer waiver can now name the PR's base as well as its head:
  `<!-- specflow-verifier:waive sha:<40-hex head> base:<40-hex base> -->`.
  A bound waiver is judged the same way a verifier marker is. If a
  retarget gives the head a different merge base, the waiver is refused as
  `waiver-base-mismatch`.
- A legacy waiver (`sha:<head>` only) still works until the PR's timeline
  records a base event at or after it. After that it is refused as
  `waiver-unbound-retargeted`, or as `waiver-timeline-unknown` when the
  timeline cannot be read (fail closed). The fixtures are
  `tests/governance/fixtures/attestation/103` to `114`.
- **What an instance owner sees:** `run-verifier.sh` and the classifier
  print the bound form. A failed `release-check` names the remedy. A
  waiver is never a required step: it is a maintainer's decision to merge
  past a `REQUEST_CHANGES`. If you do waive your first upgrade PR to 3.2.1,
  use the legacy form: that PR is judged by your v3.2.0 `main`'s
  classifier, which rejects the bound form as `malformed` (the migration,
  "How 3.2.1 reaches you").

**The habit-tracker example's home and the demo re-tag path (P7 Build 2, PR #64; REQ-391, REQ-392, REQ-306, REQ-324)**

- `docs/examples/habit-tracker/README.md` is the home of the second worked
  example, and `CLAUDE.md`'s Canonical Example manifest has an entry for
  it. A tauri instance keeps it; other stacks drop it. Its Status line
  still reads `pending the maintainer's walk`, so no walk has happened.
- `docs/examples/README.md` records the walk's checklist (M1 to M6). It
  also records REQ-392's external-product gate as not met.
- The released-document rule for the demo re-tag's follow-up is pinned in
  a governance test only: `demo_kl_ok` in
  `tests/governance/test_verify_release.sh` allows the removal of the
  demo's stale fallback section from `0.0.1-demo-known-limitations.md` only
  once `v0.0.1-demo` is SSH-signed by a listed, unrevoked key whose
  principal is the tagger. `verify-release.sh` and `release_gate.py` are
  unchanged since v3.2.0 and enforce nothing about that section.

**Two helpers from the backlog (PR #74; REQ-371, REQ-385, REQ-360, REQ-306)**

- **Ask before merge or push to `main` (BL-001).** `.claude/settings.json`
  gains `permissions.ask` rules for `gh pr merge` and for pushes to
  `main`. It also registers a PreToolUse hook,
  `scripts/lib/specflow/push_guard.py`, which resolves a `git push` to its
  destination ref. In a Claude Code session, a merge or a push to `main`
  now asks you first. It asks; it never denies. It is a local convenience,
  not a control: any PR can edit project hooks, and branch protection on
  `main` is unchanged.
- **Run new tests inside a scaffolded instance (BL-021).**
  `scripts/run-instance-tests.sh` copies the template, initialises an
  instance for each stack the change touches, and runs the new or changed
  governance tests there. It prints every SKIP. It is for the template
  source; in an instance it exits 2.

**A user guide (PR #72; REQ-308)**

- `docs/getting-started.html` covers:
  - the idea's five sections, with a worked example;
  - the setup prompts, and the push and `configure-repo.sh` steps that
    init does not do;
  - the three lanes and the seven confirmation points;
  - the verifier run, and the limit of solo mode.

  `README.md` points to it before setup step 0.
  `tests/governance/test_user_guide.sh` checks the guide's claims against
  the code.

**Smaller additions (PR #74; REQ-380, REQ-332, REQ-311)**

- The plan template has an optional inventory step for files that a
  stricter gate may fail (BL-027).
- `test_spec_lifecycle.sh` checks that `extends:` and `extended_by:` are
  symmetric (BL-032). It also fails on the two spec-frontmatter defect
  shapes found at 3.2.0: an `amended:` item at column 0, and an unescaped
  inner double quote (BL-035).
- `ci.yml` has a concurrency group keyed on the PR number. A newer run of
  the same PR cancels the superseded one (BL-039).
- `check-review`'s three refusal reasons from PR #66 are now pinned by
  fixtures (BL-040).

## Changed

**The python image runs as a non-root user from a hash-pinned lock (PR #65, Task 1.4; REQ-351, REQ-390, REQ-303)**

- `stacks/python/Dockerfile` installs `requirements-runtime.txt` with
  `--require-hashes --no-deps --only-binary :all:`, then the wheel alone,
  then runs `pip check`. It runs as `USER 10001`.
- `release-image.sh` adds the committed runtime lock to the build context,
  and refuses a commit without it.
- `rollback`, with nothing running, names `deploy <X.Y.Z>` as the
  recovery.
- **What an instance owner sees:** a python instance gains
  `requirements-runtime.in` and `requirements-runtime.txt`, which it must
  commit. Its image no longer runs as root (SEC-011, fixed).

**`release-sign.sh` signs only the committed entitlements (PR #65, Task 1.3; REQ-352, REQ-386)**

- A `signing: apple` bundle is always signed with the committed
  entitlements: the project's file, else the pack's, with
  `get-task-allow` removed.
- The entitlements the bundle embedded are only compared. A key the
  committed set lacks, or grants a different value, stops the script with
  exit 1 before anything is signed (SEC-005, fixed).
- The flutter checklist now notarizes a zip of the signed `.app`, staples
  the `.app` itself and zips it again (a zip cannot be stapled). Both
  checklists name the refusal of an embedded key that the committed set
  lacks or grants with a different value (PRs #65, #68). PR #73 records in
  the flutter checklist that Flutter 3.47.6 builds universal, so an
  instance that needs Intel Macs can drop `ARCHS = arm64`.

**The verifier's CI log and gitleaks config (PR #65; REQ-313, REQ-385)**

- On a stacked PR, `verifier.yml` now prints the fixed `main` bootstrap
  line itself. The base's own classifier text still appears, labelled and
  defanged (SEC-020, open at 3.2.0, now accepted).
- The findings scan reads `main`'s `.gitleaks.toml`, never a stacked
  base's (SEC-021, half fixed).

**The constitution: amendment D (PR #75; REQ-396)**

Twelve articles still. No article is renamed or renumbered, and no rule
gets stricter. The "How to apply" lines now say exactly what each
mechanism does:

- `art-naming-tagging`: the task-id form (`Task N.M`, `TASK-NNN`) is
  convention (no mechanism). The slug check's two exemptions are stated:
  archived reviews, and documents with `status: superseded` in their first
  20 lines.
- `art-secrets-hygiene`: sessions are denied reads of `.env` and `.env.*`;
  the verifier is denied every `.env*` name.
- `art-review-gate`: a PR is needed for a source file under the stack
  pack's `source_roots`, not only `src/`.
- `art-threat-driven-security`: `check-suppressions.sh` is run by
  `test_suppressions.sh` (gates section 3).
- `art-formal-verification`: the contract-extraction step is convention
  until v3.3.

`.claude/rules/review-gate.md`'s patch tier now admits one more change: a
rubric-only reduction of `medium_cap` to the default, 5. Any other
`medium_cap` change still needs its own reviewed PR. The v3.2 spec gains
REQ-396 and one `amended:` entry (amendment D), and its Compliance line now
counts four amendment PRs.

## Fixed

- **`main` red after a squash-merged ship (PR #66; REQ-332, REQ-340).**
  `floor.py check-review` failed on `main` after PR #62's squash merge. The
  merge dropped the commit that the 3.2.0 review's Floor summary names.
  `check-review` now accepts a released review only when both hold:
  - `v<version>` is on `HEAD`'s history;
  - the file is byte-identical to its copy at that tag.

  Before the tag, the failure message names the window between the merge
  and the tag.
- **SEC-005 (medium):** `release-sign.sh` signed the bundle's embedded
  entitlements, not the committed file. Fixed by PR #65 (see Changed).
- **SEC-006 (medium):** a waiver named a head only, so it survived a
  retarget that changed the diff. Fixed by PR #65 (see Added).
- **SEC-011 (medium):** the python image ran as root, with no hashed
  runtime install. Fixed by PR #65 (see Changed).
- **The `verify-release` stop-path fixture** used literal epochs, and went
  red when the clock passed them on 2026-10-04. It now uses offsets from
  the seed commit (PR #70; REQ-324).

### Guided proposals

These are the go/no-go decision and the acknowledgements that REQ-389
places at the ship PR (`.claude/commands/release.md`, `security-review.md`).
They are recorded here because no gate checks them on a ship PR:

- **Go/no-go (decision).** Go. The decision is the maintainer's merge of
  this ship PR (kpingali123). Merging publishes nothing by itself. The tag
  the maintainer creates afterwards does, after `release.yml` replays the
  gate at the tag. Tag by 2027-01-30 at the latest (rule 5). The review's
  Floor-summary commit is this PR's base, `ca394b5`, which a squash merge
  keeps on `main`, so `main`'s `check-review` passes before the tag:
  nothing on `main` flags the release while it is untagged.
  - Before tagging, confirm by hand (the PR template's RELEASE checkbox):
    `v3.2.0` exists, is SSH-signed and sits on PR #62's merge commit;
    PR #62's `gates` and test-first checks were green at its merge; this
    PR's are green at its merge. `release.yml` replays only gates
    section 7 at the tag, so a published Release proves neither. Then run
    `scripts/release-tag.sh 3.2.1 --dry-run`, then `/release --tag 3.2.1`
    on the merge commit.
  - Rationale (plain English): this release brings to instances three
    security fixes that have been on `main` since 2026-10-04. They cover
    app signing, waivers and the python image. It also brings the
    pinned-tool bump and the guide. Nothing is left open. The eight
    accepted mediums are known residuals, each with an owner, a date and
    a planned fix. Their fixes wait for v3.3 or for the first signed
    instance release, and the maintainer chose to ship now rather than
    hold these fixes back.
  - What this means for you: v3.2.1 fixes SEC-005, SEC-006 and SEC-011 for
    instances that take it. The factory's medium cap stays at 8 until
    shortly after the Release, and no later than 2026-12-15. An instance's
    own cap is unaffected (5).
- **Severities and dispositions (acknowledgements).** Every severity in
  `docs/security/3.2.1-review.md` is the author's provisional score, and
  so is every entry in `docs/security/3.2.1-disposition.md`. Each score
  uses a base CVSS v4.0 vector and its band from `cvss4.py`; each
  disposition follows ADR-002. They are acknowledged as such. Three of
  them rest on the author's judgement and are named here so that the
  merge acknowledges them (only the next second reviewer confirms a severity):
  - SEC-020's 5.2: 3.2.0 scored it 7.0 (high) when the workstation was
    taken as the vulnerable system.
  - SEC-021 stays low. As a medium it would be a ninth accepted medium,
    over the cap.
  - SEC-022's new 2.0.

  No `confirmed_by:` is written. The template source has no
  `.specflow.yml`, so the verifier reads `Profile: guided` and its
  `APPROVE` is the recorded second review (REQ-314). The next second
  reviewer confirms or rescores each severity.
  - Rationale (plain English): the factory has one maintainer and an
    automated second review. The scores are honest best readings, not
    checked by a second person.
  - What this means for you: an instance on the guided profile gets the
    `confirmed_by:` step from `/next` at its own ship PR. The factory's
    release records carry the verifier's verdict instead.
- **The expiry date (acknowledgement).** Every accepted entry expires on
  2027-01-31. That replaces the 2026-12-15 that P7 plan R18 and the
  threat model record, and, for SEC-010 and SEC-012, 3.2.0's 2026-11-15.
  - Rationale (plain English): one later date keeps a tag made near the
    planned 2026-11-15 from lapsing the entries, and keeps them from
    lapsing together with the cap override.
  - What this means for you: the threat model's dates are brought into
    line by the retrospective's re-dating patch PR. Until it merges, the
    two records differ.

## Breaking

None. No required check is renamed, no file format changes, and amendment
D changes the constitution's wording, not its rules. Three changes can
still ask something of an instance's own files after it takes 3.2.1. Each
is a fix to those files, not a change of process:

- **Spec frontmatter (PR #74).** `test_spec_lifecycle.sh` (gates section
  3) now fails on either of these in your own `docs/specs/`:
  - an `extends:` that the extended spec does not list under
    `extended_by:`, or the reverse;
  - an `amended:` item at column 0, or one with an unescaped inner double
    quote.

  Correct the frontmatter. The failure names the file and the line.
- **python instances.** Commit the new `requirements-runtime.in` and
  `requirements-runtime.txt`. `release-image.sh` refuses to build the
  image without the lock (migration §1).
- **`signing: apple` instances.** A bundle whose dependencies embed an
  entitlement key that the committed file lacks now stops signing
  (exit 1), where before it was signed. That is SEC-005's fix. It can
  surface at the first signed release after the upgrade.

**Still broken for you: python and v3.1 instances cannot publish their
first release yet (BL-034).** 3.2.1 does not fix it. `release-tag.sh`
exits 11 (`previous-untagged`) because the instance holds the demo's
release notes but not its tag. There is no workaround the gates accept;
do not tag the demo. Take 3.2.1 anyway: its waiver, spec and gate fixes
apply to every PR now, and its image fixes apply at your first ship. The
known-limitations says what to do.
