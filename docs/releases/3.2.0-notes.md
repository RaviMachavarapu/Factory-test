# v3.2.0 Release Notes

SpecFlow Factory v3.2 is the first release of the template since the
`v0.0.1-demo` walk-through of v3.1. It covers plans P0 to P6 of the v3.2 spec
(`docs/specs/2026-09-25-factory-v3-2-design.md`). It is the factory's own first
release on the lanes path (`ship/3.2.0`). The `date:` above is the
reproducible build's epoch (P6 R18), not the tag's date.

These notes are for someone starting a project from the template, or moving an
existing instance up from v3.1. What changes for an existing instance is in
`docs/releases/3.2.0-migration.md`. What is still open is in
`docs/releases/3.2.0-known-limitations.md`.

## Added

**Starting a project (P1a, P1b)**

- `bash scripts/init-project.sh` sets up a working instance in one run. You can
  pass flags, or press Enter at every prompt to take the defaults: guided
  profile, lanes path, python stack, solo mode. The result is on `main` with
  green gates, `.specflow.yml`, the stack's pack, and a release hook
  (REQ-300, REQ-301, REQ-304, REQ-305).
- Three stack packs under `stacks/<stack>/`: **python** (services and CLIs),
  **tauri** (Mac desktop) and **flutter** (the macOS build of a multi-platform
  app). Each pack ships its pinned toolchain action, gates, security audits,
  release hook and a skeleton that passes the gates with no hand edits
  (REQ-303, REQ-304).
- In-repo commands `/specify`, `/specflow-plan`, `/specflow-tasks` and `/analyze`
  (REQ-302). A README audience block for both profiles, and a
  `docs/GLOSSARY.md` of every pipeline term (REQ-308).
- Your project gets none of the template's own design documents or Dafny
  models. Its REQ numbers, traceability and proofs are its own (REQ-306).

**The lanes path and `/next` (P5)**

- Two paths, set by `.specflow.yml`'s `path:`. **lanes** has three PRs per
  feature: `design/<slug>`, `build/<slug>-N` and `ship/<version>`.
  **regulated** has seven phase branches (REQ-340).
- `/next` (`scripts/next.sh`) works out where the pipeline is from branches,
  PRs and files, never from a state file, and prints the one next step. In the
  guided profile it also runs that step, and pauses only at the listed
  confirmation points (REQ-341, REQ-342). Its decision function
  (`scripts/lib/specflow/state.py`) is proved in Dafny in the template source.
  It never prints a merge command for a head that lacks an `APPROVE` or a
  waiver, and the command it prints merges only that head
  (`--match-head-commit`; REQ-385).
- `/next --json` prints the derived state. The dashboard
  (`scripts/render_dashboard.py`) now reads it (REQ-370).

**The verifier attestation and solo mode (P2)**

- `scripts/run-verifier.sh <PR>` runs the adversarial review headlessly, in a
  second terminal. It reviews the PR head in an isolated worktree: full mode
  for documents, code mode for code. It then posts a comment whose marker line
  is written by the script, not the model (REQ-310, REQ-311, REQ-313).
- The required `verifier` check passes only on an `APPROVE` marker or a
  maintainer waiver for the current head, from someone with a writing role on
  the repository (REQ-311, REQ-382). In solo mode the verifier's `APPROVE` is
  the recorded second review. Team mode adds one human approval
  (REQ-312, REQ-314).
- `scripts/configure-repo.sh` requests branch protection with the two stable
  check names, `gates` and `verifier`. When a free private repository refuses,
  it says so in plain English (REQ-312).

**Mechanised gates (P0, P3)**

- Gates follow the plans that claim each REQ, so a spec delivered over many
  plans never turns `main` red (REQ-380, REQ-327).
- Test-first per commit: `scripts/check-test-first.sh` (REQ-321). Every claimed
  REQ is cited by a test: `scripts/check-covers.sh` (REQ-323). A coverage floor
  per toolchain that a PR cannot lower: `coverage_min`, read at the base
  (REQ-325).
- Each security finding carries a CVSS v4.0 vector, and its severity is derived
  from that vector. A proved decision function decides whether a version may
  ship: `scripts/check-security-disposition.sh` (REQ-322, ADR-002).
- `scripts/verify-release.sh` is the release gate at PR time. It checks the
  three release documents, the disposition gate, the REQ claims and proofs,
  and the previous release's tag (REQ-324).

**The security floor (P4)**

- Every gates run, local or in CI, runs the security floor: gitleaks over the
  full history, osv-scanner over every tracked lockfile, then the stack's own
  audits. A missing floor tool is a hard failure with an exact install line
  (REQ-330, REQ-331).
- Every suppression cites a live `SEC-NNN` (REQ-388). `/security-review` pastes
  a rendered `## Tools run` table with a digest, not a hand-written one
  (REQ-332). The threat model template carries a ten-domain checklist
  (REQ-333).
- CI installs floor tools from checksum-pinned release assets, and every
  GitHub Action is pinned to a commit SHA (REQ-334).

**Releases: the signing anchor and `/release --tag` (P6 Build 1)**

- `.github/allowed_signers` holds the public SSH keys that may sign release
  tags. It is read as committed at the anchor: the newest earlier SSH-signed
  release tag, else trust on first use. `.github/revoked_signers` revokes a key
  (REQ-383).
- `/release --tag <version>` runs `scripts/release-tag.sh` after the ship PR has
  merged. It signs the merge commit with SSH, checks the signature against the
  anchor and pushes the tag. Before signing, it runs the same previous-release
  and tag-time checks `release.yml` runs, so it never pushes a tag
  `release.yml` would refuse. `/next` prints the command once the ship PR has
  merged (REQ-383, REQ-342).
- `configure-repo.sh` also requests the `release tags` ruleset, which keeps
  `v*` tags from non-admins. It also creates the `release` environment and
  turns rebase-merge off. `--check-ruleset` and `--check-environment` report
  their state read-only (REQ-383, REQ-386).

**Releases: the CI-built manifest (P6 Build 2)**

- Manifest schema 2 marks each artifact `reproducible: true|false`. The ship
  PR's notes record only the reproducible rows. Source archives are
  uncompressed `.tar` files of the committed tree, without `docs/releases/` and
  `docs/security/`. Every file's time is midnight UTC of the notes' `date:`
  (REQ-384, R18).
- The required `gates` check rebuilds the reproducible subset from the PR head
  and compares it with the notes' `## Artifacts` table (R26).
  `.github/workflows/release-build.yml` builds the same subset on demand and
  uploads it as the record for `/release` to copy.

**Releases: `release.yml` at the tag (P6 Build 3)**

- Pushing a `v*` tag runs `.github/workflows/release.yml`. It refuses a tag
  that is off `main`, not SSH-signed by an anchored key, or whose range holds
  a merged PR without an accepted marker, a waiver or the Dependabot
  exemption. It replays the release checks at the tag, rebuilds the
  reproducible artifacts from a clean checkout, compares them with the notes,
  smoke-runs them, and publishes a GitHub Release with every artifact and the
  job's `manifest.json` (REQ-350, REQ-390).
- These refusals bind a tag on a reviewed commit (one that carries `main`'s
  `release.yml`). The `release tags` ruleset keeps other tags out (R31). The
  Release body prints the offline `verify-tag` command and names the anchor.

**Python: the image and the deploy contract (P6 Build 4)**

- The python release hook builds a reproducible sdist and wheel from the
  committed tree (REQ-384).
- `release.yml` builds the pack's `Dockerfile` and smoke-runs the image before
  pushing `ghcr.io/<owner>/<repo>:<version>` to GHCR with the job's token. A
  re-run reuses the published digest (REQ-351, REQ-390).
- `deploy.sh` becomes a four-part deploy contract: migrate, deploy, smoke and
  rollback. `deploy-local.sh` is the local example, and rollback deploys the
  release below the running one by digest (REQ-351).

**Tauri and flutter: macOS bundles (P6 Build 5)**

- The tauri and flutter hooks build the reproducible source archive and, in a
  separate part, the macOS bundle (a `.dmg` or a zipped `.app`). `release.yml`
  builds it on `macos-15` and checks that it starts and exits within 60 seconds
  under `SPECFLOW_SMOKE=1` (REQ-352, REQ-390).
- `.specflow.yml`'s `signing: none|apple` decides the signing path:
  - **`apple`:** the bundle is signed and notarized (`scripts/release-sign.sh`)
    using five Apple secrets in the `release` environment. A secret-free job
    then verifies it.
  - **`none`:** the bundle ships unsigned, with the pack's tester instructions
    in the Release body.

  `/next --explain` prints the setting and what it means (REQ-386, REQ-354).
- An app-stack ship PR's notes carry the pack's macOS distribution checklist
  (REQ-352).

## Changed

- Spec commands are in-repo: `/specflow-plan` and `/specflow-tasks` replace
  SpecKit's `/plan` and `/tasks`, which collide with Claude Code built-ins
  (REQ-302).
- The verifier bootstrap uses the full remote-tracking ref of `main`, for
  every PR, stacked or not:
  `git show refs/remotes/origin/main:scripts/run-verifier.sh | bash -s -- <PR>`.
  A tag named `origin/main` can no longer choose the script (REQ-385, P6
  Build 3), and since the SEC-004 back-edge (PR #61) a stacked PR's base
  branch supplies data only and is never piped into bash (see Fixed below).
  Never copy the bootstrap from a CI log; use this line or the one `/next`
  renders.
- The constitution's amendments A and B (REQ-314, REQ-343) take effect:
  - `art-review-gate`: the solo second review, the waiver rules and the
    Dependabot exemption with its residual.
  - `art-branch-as-state`: both paths' branch names, squash merges and
    `.specflow.yml` as configuration.
- `art-release-readiness` is judged after the merge. The ship PR must not
  carry `v<version>`. The next ship PR's `verify-release.sh` checks the
  previous release's tag.
- The demo's own release hook was retired. Each stack's
  `scripts/release-<stack>.sh` follows `scripts/release-stack.sh.template`'s
  contract (REQ-305).
- `scripts/requirements.txt` is hash-pinned, and lockfiles are no longer
  ignored by git (REQ-334).

## Fixed

- P0 fixed two traceability-checker bugs. One is that an empty-quoted
  frontmatter value is now read as empty. A draft spec can now merge before
  its proofs exist (REQ-327).
- `verify-doc.sh` reads the file directly, so it no longer gives false warnings
  on large documents.
- A follow-on design lane (`design/<spec slug>-pN`) now finds its spec through
  its plan's `spec:` frontmatter instead of reporting no spec (P6 Build 5).
- SEC-004 (high): the verifier bootstrap for a PR stacked on a branch other
  than `main` piped that unreviewed branch's own `run-verifier.sh` into bash.
  It is now always `main`'s reviewed script
  (`git show refs/remotes/origin/main:scripts/run-verifier.sh | bash -s -- <PR>`),
  a stacked base supplies data only and is named, never executed, and `/next`
  says to merge the base PR first, then retarget (PR #61, the
  `build/sec-SEC-004` back-edge).

## Security

- Security review: `docs/security/3.2.0-review.md`. Disposition:
  `docs/security/3.2.0-disposition.md`. The scores are CVSS v4.0 base vectors.
  Every severity is provisional (solo mode).
- **Final.** The SECURITY exit gate passes:
  `check-security-disposition.sh --version 3.2.0` exits 0. At the review's
  first commit it failed on an open high and on the medium cap; each was
  resolved by its own attested PR to `main`, onto which this branch was
  rebased:
  - **SEC-004 (high, fixed).** Fixed by PR #61, the `build/sec-SEC-004`
    back-edge, merged 2026-10-03 as `33a4984` (see Fixed above). What the fix
    leaves open is SEC-020 (medium, open: the CI log of a stacked PR prints
    the unreviewed base's bootstrap hint — never copy it from a log; P7
    Build 1 fixes it) and SEC-021 (low, accepted: a stacked base still
    supplies the verifier run's gitleaks config and prompt).
  - **The medium cap.** Nine mediums are accepted or deferred against
    `medium_cap: 10`, raised from 5 for this release by the maintainer's
    decision of 2026-10-03 (PR #59, recorded in `docs/security/RUBRIC.md`
    with the nine ids). The override returns to 5 by 2026-10-12 unless the
    P7 retrospective re-decides it, so the gate is calendar-dependent after
    that date. The two open mediums, SEC-005 and SEC-020, are outside the
    cap.
  - **SEC-005 (medium, open).** In a `signing: apple` instance,
    `release-sign.sh` signs and notarizes the entitlements that the unsigned
    bundle embedded, not the committed entitlements file. A build hook in a
    dependency can therefore drop the app sandbox, or add
    `cs.disable-library-validation`, in a release signed with the maintainer's
    Developer ID. It has no disposition yet. It does not affect the template,
    python instances or `signing: none` bundles.
- **Accepted:** SEC-007, SEC-008, SEC-009, SEC-010, SEC-011, SEC-012, SEC-013,
  SEC-014, SEC-015, SEC-016, SEC-017, SEC-018, SEC-019 and SEC-021.
  Each one is a residual the threat model records, or one the back-edge's
  review raised, with an owner and an expiry.
- **Deferred:** SEC-006, waiver base binding, to P7 Build 1 (R4; amendment C,
  PR #60, did not change the waiver grammar).
- Each open, accepted and deferred id is listed in
  `docs/releases/3.2.0-known-limitations.md`, with its expiry where it has
  one.
- Floor tools run for this review: gitleaks 8.30.1 and osv-scanner 2.6.0, all
  clean (the review's `## Tools run`).

### Guided proposals

The go/no-go decision and the acknowledgements REQ-389 places at the ship
PR (`.claude/commands/release.md`, `security-review.md`), recorded here
because no gate checks them on a ship PR:

- **Go/no-go (decision).** Go. The decision is the maintainer's merge of the
  ship PR (kpingali123): merging publishes nothing by itself — the tag the
  maintainer creates afterwards does, after `release.yml` replays the gate
  at the tag.
  - Rationale (plain English): every blocking finding was fixed or decided
    on its own reviewed PR before this one; what stays open is named,
    scored and owned. SEC-005 affects only `signing: apple` instances: a
    dependency's build hook can drop `app-sandbox` or add
    `cs.disable-library-validation` in a release signed with the
    maintainer's Developer ID, so until it is fixed those instances compare
    `codesign -d --entitlements :-` on the signed app with the committed
    entitlements by hand (known-limitations says how). SEC-020 is reached
    only when a maintainer copies a bootstrap line from a CI log. The
    template, python instances and `signing: none` bundles are unaffected.
  - What this means for you: v3.2.0 ships with two open mediums and one
    cap override that the P7 retrospective must re-decide by 2026-10-12.
- **Severities and dispositions (acknowledgements).** Every severity in
  `docs/security/3.2.0-review.md` and every entry in
  `docs/security/3.2.0-disposition.md` is the author's provisional scoring
  (base CVSS v4.0 vector, band from `cvss4.py`; disposition under ADR-002),
  acknowledged as such. No `confirmed_by:` is written: the template source
  has no `.specflow.yml`, so `run-verifier.sh` resolves `config.DEFAULTS`
  and its header reads `Profile: guided`, while "engineer" is a session
  convention (`docs/GLOSSARY.md:12`, P7 R6); solo mode has no second human
  reviewer, so the verifier's `APPROVE` is the recorded second review
  (REQ-314) and the next second reviewer confirms or rescores each
  severity. The acknowledgements are recorded here, under the guided
  profile's heading, although the template source runs engineer by
  convention.
  - Rationale (plain English): the acknowledgement route is written for a
    guided instance with a maintainer who confirms; the factory itself has
    one maintainer and an automated second review, and reads as guided to
    the verifier only because it has no configuration file.
  - What this means for you: an instance on the guided profile gets the
    `confirmed_by:` step from `/next` at its own ship PR; the factory's
    release records carry the verifier's verdict instead.

## Breaking

For an instance moving up from v3.1, `docs/releases/3.2.0-migration.md` gives
the steps. The breaking changes are:

- **Required checks.** The required check names are `gates` and `verifier`.
  Re-run `configure-repo.sh`.
- **Verifier on every PR.** A PR needs a verifier `APPROVE` marker or a
  maintainer waiver before it can merge.
- **Gates that now fail.** These block a PR that v3.1 let through:
  - test-first per commit;
  - `# Covers:` citations;
  - the coverage floor;
  - the security floor (gitleaks, osv-scanner and the stack's audits, with
    missing tools a hard failure).
- **Plan frontmatter.** Plans dated 2026-09-25 or later need `implements:`.
- **Security document format.** Reviews and dispositions use the block schema
  `specflow-security/1`, with a CVSS v4.0 `cvss_vector:` on every finding.
- **Release hooks.** They write manifest schema 2 and archive the committed
  tree, never the working tree.
- **Release tags.** These are SSH-signed with `/release --tag`. `release.yml`
  refuses a GPG-signed tag (P6 R27).
