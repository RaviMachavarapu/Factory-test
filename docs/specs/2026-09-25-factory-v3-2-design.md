# Factory v3.2 — Idea In, Tested Ship-Ready Product Out

## Overview

v3.2 makes the SpecFlow Factory template deliver its objective: a user with only an idea clones the template, runs the pipeline, and gets a product that is fully tested and ready to ship. It implements the six-item roadmap from the 2026-09-25 template objective review (`docs/reviews/2026-09-25-template-objective-review.md`): a first-run path that works, verifier attestation that covers code and supports solo users, mechanized versions of every gate the constitution promises, a security tool floor, a three-lane pipeline with an orchestrator and two user profiles, and a real ship target per stack. This revision (draft 2) incorporates the five-reviewer fresh-eyes synthesis `docs/reviews/2026-09-25-factory-v3-2-spec-review.md`.

### Scope
In: **Founder (guided profile)** — copy-paste terminal skills; gets a pipeline where Claude makes technical decisions and the human confirms plain-English summaries and merges.
In: **Engineer (engineer profile)** — solo or small team; gets a pipeline that works out of the box for Python, Tauri or Flutter, with honest, mechanical gates.
In: **Reviewer / maintainer** — gets one enforcing file per constitution article and a governance test per script.
Out: **Windows/Linux desktop, Android, iOS builds** — v3.3; only macOS desktop bundles are built in CI.
Out: **Code signing, notarization, store submission automation** — a documented checklist with hook points and secret names, not automation.
Out: **Node-only or Go products** — not first-class stacks in v3.2; the stack-pack layout admits them later.
Out: **Runtime-contract extraction for `[verifiable]`** — deferred to v3.3; `[verifiable-model]` remains the tag in use (constitution amended accordingly, REQ-326).
Out: **Clause-level contract-to-test mapping and `tests/e2e/`** — REQ-level Covers only; `tests/e2e/` is removed from init.

## Problem Statement

The review reproduced three walls a fresh instance hits before anything is tested: the `/speckit.*` commands the pipeline names do not exist in the repo, implementation PRs can never pass the verifier attestation because the verifier only reads markdown, and RELEASE looks for a per-stack hook that init never creates. Behind them, "fully tested" has no machine check, "shipped" ends at a gitignored tarball, no security tooling runs, only 2 of 12 constitution articles are mechanically enforced, and a solo user cannot satisfy the review gate at all. The template has only ever been run on itself.

## User Personas

### Persona: Founder (guided)
- **Role:** Non-technical founder with a product idea (the worked example: a macOS habit tracker).
- **Goal:** Get a working, tested, releasable first version without making technical decisions they are not equipped to make.
- **Context:** Uses the terminal by copy-paste; has Claude Code and a GitHub account; works alone; will run one command outside Claude (the verifier) when told exactly what to type.
- **Success looks like:** Every step is one printed command; every decision is a plain-English confirmation; the end is a GitHub Release with a bundle a tester can open by following the generated instructions.

### Persona: Engineer
- **Role:** Software engineer, solo or in a team of two, building a real product on Python, Tauri or Flutter.
- **Goal:** A pipeline whose gates are real for their stack and that does not cost seven PRs per feature.
- **Context:** Comfortable with git, PRs, CI; wants to keep making technical calls; likely on a free private GitHub repo.
- **Success looks like:** Fresh instance passes gates immediately; CI runs their tests; the release job produces a verifiable artifact; nothing in the docs is a promise the tooling does not keep.

### Persona: Reviewer / maintainer
- **Role:** Approves PRs and maintains the factory.
- **Goal:** Know which file enforces each rule and trust a green check.
- **Context:** Reads the constitution, runs the verifier, merges.
- **Success looks like:** Every article's "How to apply" names its enforcing file; every script has a governance test; the retro loop has a home.

## Objectives

1. A fresh instance of any first-class stack, in either profile, passes `run-quality-gates.sh` immediately after init and reaches a GitHub Release using only the commands `/next` printed.
2. Every constitution article that says "the verifier rejects" or "blocks" names a script that does so, and a governance test proves it.
3. A solo user can complete the review gate without a second GitHub account, with the gate honestly described, and without weakening the gate for teams.
4. "Fully tested" is defined and machine-checked: per-toolchain coverage floor, test-first per commit, every implemented REQ covered by a citing test, security tool floor green.
5. "Ready to go" is produced by CI from the tag, not by a laptop.

## Non-Functional Requirements
- **Performance:** `run-quality-gates.sh` on a fresh instance completes in under 3 minutes on ubuntu (python) excluding toolchain download; app-stack gate runs on `macos-15` under 10 minutes with warm caches. A free-plan private repository has about 200 macOS minutes per month; one Tauri release costs about 100 of them, which is why app first-run tests are scheduled, not per-PR.
- **Security:** No API key anywhere; verifier runs on subscription auth in an isolated worktree with project settings disabled; all CI tool downloads pinned by version and checksum; workflows read-only by default.
- **Scalability:** Stack packs are additive; adding a stack is one directory plus its governance-test entry.
- **Compliance:** Every change to `constitution.md` lands in one of four amendment PRs (A with P2, B with P5, C in P7, D in its own design lane after the v3.2 retrospective), each citing the REQs that motivate it.

## Verification Identification

Two tags (`art-formal-verification`): `[verifiable]` = Dafny proof + runtime contract (deferred to v3.3); `[verifiable-model]` = Dafny proof of a contract model + tests of the real implementation.

Tagged in this spec: REQ-322 (security-disposition decision: a data-integrity rule) and REQ-341 (pipeline state derivation: a state machine). Both are pure functions in `scripts/lib/specflow/` (REQ-381). Not tagged: scaffolding, CI wiring, documentation, and tool invocation requirements, which are exercised by governance tests only.
