**The stacked-base verifier instruction (P5 R22).** For a PR whose base is
not `main`, the factory's documented bootstrap (`review-gate.md` step 3,
the PR template, `/next`'s `_verifier_line`) was, before the back-edge,
`git show refs/remotes/origin/<base>:scripts/run-verifier.sh | bash -s -- <PR>`
(never run this form; see the fix record below).
The base is a branch that the PR's author chose and that no review has
approved. Any writer can push a phase branch with a rewritten
`run-verifier.sh` and open a PR stacked on it. A maintainer who runs the
instruction then runs that script with their Claude OAuth and `gh` sessions
(an org admin token). `/next` prints a warning ("read it first"), but a
warning is not a control.

Remediation (the back-edge's to choose): for a non-`main` base, render no
bootstrap and print "merge #<base PR> first, then retarget". Alternatively,
bootstrap from `refs/remotes/origin/main`'s copy.

`build/sec-SEC-004`, merged to `main` on 2026-10-03 as `33a4984`; verifier

- A stacked base without the entry point is refused with exit 3, and

**Signing trusts the entitlements the unsigned bundle embedded.** PR #58
verifier run 2 raised this, and no residual records it yet. In an app
instance's `sign` job, `release-sign.sh` reads the entitlements with
`codesign -d --entitlements :-` and prefers them to the project's committed
file. It signs them under the Developer ID and notarizes them, removing only
`get-task-allow`. Those entitlements come from the secret-free `bundle` job,
which ran third-party build code (`build.rs`, npm or pub hooks). Such code
can already change the binary. But only an entitlement can drop
`app-sandbox` or add `cs.disable-library-validation`, and an entitlement
change looks like configuration, not code. That widens what a release
signed with the maintainer's identity can reach on a user's Mac.

Remediation (proposed for P7): refuse any key in the embedded set that the
committed entitlements file does not list, and print the difference key by
key.
