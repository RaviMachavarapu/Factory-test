`/release <version>` writes the ship PR's documents (steps 1-7 below). `/release --tag <version>` runs only "Tag the release", after the ship PR has merged. When `$ARGUMENTS` begins with `--tag `, the version is the word after it: skip to "## Tag the release", read `<version>` there wherever the text says `$ARGUMENTS`, and run no other step.

You are entering the RELEASE phase for `v$ARGUMENTS`.

Read `constitution.md` article `art-release-readiness`.

Produce in order:

1. `docs/releases/$ARGUMENTS-notes.md` with frontmatter (`version`, `date`, `specs`, `adrs`, `security_findings_accepted`, `security_findings_deferred`) and body organized as Added / Changed / Fixed / Security / Breaking.

2. `docs/releases/$ARGUMENTS-migration.md` with frontmatter (`version`, `from_versions`, `breaking`) and step-by-step upgrade instructions.

3. `docs/releases/$ARGUMENTS-known-limitations.md`. Auto-include every `status: accepted` and `status: deferred` finding from `docs/security/$ARGUMENTS-disposition.md` (by SEC-NNN id).

4. Resolve the active per-stack hook through `packinfo.py` at the ship PR's base (`git fetch origin main` first; the full ref, as CI passes it, since a tag named `origin/main` would shadow the short name; `--ref` reads instance-ness and the pack as committed there, as `verify-release.sh` and `release-build.yml` do, so a branch that adds or deletes `.specflow.yml` or `.stack` cannot swap the hook): `HOOK="scripts/release-$(python3 scripts/lib/specflow/packinfo.py --root . --ref refs/remotes/origin/main stack).sh"`. Commit the three documents (the notes with `date:` first in the frontmatter: it is the epoch of the reproducible build, R18) on the release branch you are on — `ship/<version>` on the lanes path, `phase/release` on the regulated path (`.specflow.yml`'s `path:`); never create the other path's branch. Bring that branch up to date with `main` first — `git rebase refs/remotes/origin/main` (the full ref, for the same reason; the PR does not exist yet; `gh pr update-branch` applies only once the PR exists, on a later push) — so the artifact CI builds is built from the tree you push, the tree strict protection keeps up to date until the merge. Then push it (`git push -u origin HEAD`; `git push --force-with-lease` when the rebase rewrote commits you had already pushed) and build CI's record on it: `gh workflow run release-build.yml --ref "$(git branch --show-current)" -f version=$ARGUMENTS`, wait for it (`gh run watch`), then `gh run download <id> -n release-dist-$ARGUMENTS -D dist`. CI's manifest is the record; a laptop build (`VERSION=$ARGUMENTS DIST_DIR=$(pwd)/dist bash "$HOOK"`) is a cross-check only, never the source of the rows.

5. Transcribe `python3 scripts/lib/specflow/release_manifest.py rows --manifest dist/manifest.json` into `docs/releases/$ARGUMENTS-notes.md` under a `## Artifacts` section (the reproducible rows only: filename + sha256 + size) so an auditor at the tag commit can verify checksums without re-running the hook (`dist/` is gitignored). The rows are those of the tree step 4 pushed: after any later update of the branch that changes a built path (a rebase, or `gh pr update-branch` once the PR exists — strict protection requires the branch to be up to date before the merge), dispatch `release-build` again and download its artifact again (a changed tree changes the rows, and `gates` says so). Also record, in this order:

   - the notes' Release link line, `Release: https://github.com/<owner>/<repo>/releases/tag/v<version>` (`<owner>/<repo>` from `gh repo view --json nameWithOwner`; `docs/releases/` is excluded from every archive, so the link is no fixpoint; `release.yml` creates the Release at that URL; the gate FAILs a link naming another repository than `origin`'s);
   - if no signer at all — SSH, GPG or X.509 — is configured or held in this environment (a GPG-only signer is no fallback: the tag step below refuses it, exit 5, and `release.yml` refuses a GPG-signed tag — configure SSH signing instead; and the tag step never falls back by itself: with no signer it refuses, exit 3, until you pass `--annotated` explicitly — in the guided profile only after `/next`'s `unsigned-tag` confirmation point — and it tags annotated only once this line is on `main`, exit 4), the annotated-tag fallback in `docs/releases/$ARGUMENTS-known-limitations.md` now, before the gate runs below, as this line (the next ship PR's `verify-release.sh` reads exactly this `- Annotated-tag fallback:` line prefix; a line that merely mentions an annotated tag or a fallback records nothing):

     ```
     - Annotated-tag fallback: `v$ARGUMENTS` is annotated, not signed (no signer — SSH, GPG or X.509 — at tag time, so the tag step's `--annotated` creates it by the engineer's explicit choice); follow-up: re-tag it signed once a key is configured.
     ```

     The tag is created later, possibly on another machine, so the tag kind is decided again at tag time by `/release --tag` ("Tag the release"), which also reports it after tagging;
   - the tag ruleset: run `bash scripts/configure-repo.sh --check-ruleset`; when it reports `absent`, `unreadable` or `present but ineffective`, add to known-limitations the line `- Tag ruleset: <state>; without it anyone with write access can push a v* tag (with it, a repository admin still can: the ruleset's admin bypass), and release.yml's refusals bind only a tag on a reviewed commit (one that carries main's release.yml); verify a release offline with the Release body's verify-tag command (P6 R31)` (its `release.yml` clause holds where `.github/workflows/release.yml` exists on `main`; never a claim that `release.yml` refuses a tag it never sees);
   - for the python stack, the line `- Reproducible builds: the sdist and the wheel depend on the runner's Python and zlib; CI's build (release-build.yml, then release.yml at the tag) is the record, a laptop build is a cross-check only (P6 R18)`.
   - for the app stacks only (`tauri` and `flutter`: the stack is the governing pack's, `python3 scripts/lib/specflow/packinfo.py --root . --ref refs/remotes/origin/main stack`, as in step 4 — python and the template skip every item below and leave `signing:` alone; P6 R22, R23, R35):
     1. append `docs/releases/store-checklist.md` to `docs/releases/$ARGUMENTS-notes.md` under a `## macOS distribution checklist` heading — `release.yml` cannot edit a tagged file, and `verify-release.sh` FAILs an app-stack ship PR whose notes lack that heading (REQ-352). The checklist ends with its re-run sentence, which the notes carry verbatim (REQ-386): "Re-run the tag after adding the secrets and observe `signed: true`."
     2. read the `release` environment's secrets (never the repository's, which hold none: R32): `gh secret list --env release --json name`, parsed with python3. All five of `APPLE_CERTIFICATE_P12`, `APPLE_CERTIFICATE_PASSWORD`, `APPLE_ID`, `APPLE_TEAM_ID` and `APPLE_APP_PASSWORD` present is `apple`; anything else, and an unreadable list (say so in the notes), is `none`;
     3. run `bash scripts/configure-repo.sh --check-environment`; when it reports `absent` or `unreadable` (or `present but ineffective`), add to known-limitations the line `- Release environment: <state>; without it the Apple secrets would be repository secrets that any workflow run can read, and the signing jobs' environment gate does not hold (P6 R32)`;
     4. when `.specflow.yml`'s `signing:` differs from what step 2 found, write it: `python3 scripts/lib/specflow/config.py --root . write signing=<none|apple>` and commit it with the release documents (`config.py validate` accepts `none` and `apple` only; REQ-354);
     5. with `none`, add to known-limitations the line `- Unsigned bundle: the macOS bundle is not signed or notarized (no Apple secrets in the release environment); release.yml records signed: false and attaches tester instructions (REQ-386)`, and write `docs/releases/$ARGUMENTS-tester-instructions.md` from `docs/releases/tester-instructions.md` with `<version>` replaced by `$ARGUMENTS` and `<app>` by the application's name — `verify-release.sh` FAILs an app-stack `signing: none` ship PR without that file, and `release.yml` puts it in the Release body (R23).

6. Run `bash scripts/verify-release.sh --version $ARGUMENTS` — the PR-time release gate (REQ-324). It compares the notes' rows with a build of the reproducible subset made in the gates check, and runs `run-quality-gates.sh` last, so nothing above has seen the notes before their `## Artifacts` table exists (R14: a gates run before step 5's transcription would fail the Artifacts check). Must exit 0.

7. Open the PR per `.claude/rules/review-gate.md` (the branch is already pushed). Include `release-build`'s manifest in the PR description.

## Guided profile

Read only when `python3 scripts/lib/specflow/config.py get profile --default guided` prints `guided`. Ask only when the user ran `/release` directly. When `/next` ran this command it asks nothing here: at `ship-pr` `/next` shows the severity scores and the dispositions (acknowledgements), writes `confirmed_by:` into the frontmatter of the security review and the disposition, asks go or no-go (the decision) and records the answer under `### Guided proposals` in the release notes; on the regulated path `phase/security`'s point writes the security review's and disposition's `confirmed_by:` only, and `phase/release`'s asks go or no-go and records it under `### Guided proposals` in the release notes (REQ-342 allows no other pause). At `design-pr` and `ship-pr`, after writing `confirmed_by:` (and, at `ship-pr`, the go/no-go answer) and running the gates green as `next.sh` renders them (`bash scripts/next.sh --gates`), `/next` runs `git add` on all of the lane's artifacts (new and edited) — exactly the path sets `next.md` names at that point, nothing else — and commits them — `git commit -m "docs(guided): confirmed_by: <handle> <date> — acknowledgements at design-pr (REQ-389)"`, or `…at ship-pr (REQ-389)` — and only then runs `create-pr`, so the pushed branch carries what the gates checked. Under a `### Guided proposals` heading, give each proposal a `Rationale (plain English):` line and a `What this means for you:` line, in words a non-engineer follows. ## Tag the release

`/release --tag <version>` runs only this section, and only once the ship PR has merged: `verify-release.sh`'s PR-time gate requires that `v<version>` does not yet exist, so the tag cannot be created before the merge. The session never runs `git tag` itself; `scripts/release-tag.sh` does, on the ship PR's merge commit.

1. Check out `main` and pull.
2. Where the machine holds more than one GitHub account, export the account that can push to this repository's `main` (`gh auth status`) first (`release-tag.sh`'s previous-release check and tag-time re-check use the ambient gh authentication): `export GH_TOKEN="$(gh auth token --user <account>)"`.
3. Run `bash scripts/release-tag.sh <version>`. The guided profile adds `--annotated` (`bash scripts/release-tag.sh <version> --annotated`) only after the `unsigned-tag` confirmation; that pause is `/next`'s, a convention the script cannot check — `--annotated` is the engineer path's flag, and the script prints that reminder before it proceeds. The script signs the merge commit with the SSH key, verifies the signature against `.github/allowed_signers` at the anchor with the `ssh-keygen` on PATH (pinned as `gpg.ssh.program`; a local `gpg.ssh.allowedSignersFile` is never read), and pushes the tag. Before it signs, the script runs the same previous-release check `release.yml` runs (`signers.py previous`: the previous release must be tagged and verify as released) and the tag-time re-check (`attestation.py release-check`), so it never pushes a tag `release.yml` would refuse; both read GitHub as the account you exported, while `release.yml` reads it as the workflow's `GITHUB_TOKEN`, under which a maintainer whose organisation membership is private reads as `COLLABORATOR` and their waivers are refused at the tag — keep the maintainer's membership public. Residual: this pre-push verification still trusts the local git and ssh-keygen binaries themselves; `release.yml` re-verifies the pushed tag in a clean runner (an instance initialised before `release.yml` existed has none, and the script's `next:` line says so: it checks `.github/workflows/release.yml` on `main`). The script's header lists every environment variable and git configuration key it reads.
4. Read its exit code:
   - exit 0: tagged and pushed. The script records the tag kind and, for a signed tag while known-limitations still carries a fallback line, prints the follow-up: remove that line in a follow-up docs PR so known-limitations says what shipped.
   - exit 2: pull `main` first, or the ship PR has not merged (or the tag already exists, the tree is unclean, the arguments are wrong, or the release docs on `main` differ from the ship PR's merge commit — a change after the merge ships as its own release); fix that and run it again.
   - exit 3: no signer at all (`signers.py signing-kind` prints `none`: no SSH key, no GPG key configured or held for your git email, no X.509 format). Configure an SSH one (`git config --local gpg.format ssh`, `git config --local user.signingkey <key>.pub`, and `gpg.ssh.allowedSignersFile .github/allowed_signers`) or, after the `unsigned-tag` confirmation, run with `--annotated`.
   - exit 4: **stop**. `--annotated` needs the fallback line recorded first: open a follow-up docs PR that adds the `- Annotated-tag fallback:` line (step 5 above) to `docs/releases/<version>-known-limitations.md`, merge it, then run the script again; it still tags the release's merge commit (an ancestor of `main`), not the docs PR's.
   - exit 5: only a non-SSH signer is available (`signing-kind` `gpg`: a GPG key configured or held for your git email; or `other`: an X.509 or any other `gpg.format`); the tag path accepts SSH signatures only (the pre-push verification and `release.yml`), so configure SSH signing (as for exit 3).
   - exit 6: the signed tag did not verify against the anchor (the newest earlier SSH-signed `v<X.Y.Z>` tag among the tagged commit's ancestors, else the trust-on-first-use commit); the local tag was deleted and nothing was pushed. The script prints the advice for the kind it found: `unlisted` — the key is not in `.github/allowed_signers` at the anchor; add it by PR, and it is trusted from the release after the first one tagged on a commit that lists it; `tagger-mismatch` — the tagger (your `user.email`, or `GIT_COMMITTER_EMAIL`) is not the key's principal; `revoked` — the key is in `.github/revoked_signers` at the tag or on `main`, so sign with another listed key; `revocation-unreadable` or `revocation-malformed` — git could not read that file, or a line is not `<keytype> <base64>`: fix it by PR; `anchor-off-main` or `anchor-unverified` — the newest earlier SSH-signed tag is off `main`'s first-parent history or does not itself verify, so stop and ask the maintainer; `no-anchor` — no key is listed on `main` before the tagged commit: merge one by PR first; `shallow` — fetch the whole history; `git-error` — git could not read the history (`git fsck`); `bad` — the signature itself does not verify (a BAD signature, a tag with no tagger, or `ssh-keygen` absent from PATH): check the signing key and run it again.
   - exit 7: the tag-time re-check (`attestation.py release-check`, through gh) refused a merged PR or a direct push since the previous published release, or could not run (gh or git failed — fail closed); nothing was tagged. A maintainer waiver on that PR for its merged head (on the commit, for a direct push of code), then run it again.
   - exit 8: `git ls-remote --tags` could not read the remote (authentication or network), so whether the tag exists there is unknown; nothing was tagged. Fix the access and run it again.
   - exit 9: the push failed (authentication, or the tag ruleset refused it); the local tag this run created was deleted, so a re-run starts clean.
   - exit 10: signing the tag itself failed (no ssh-agent or key loaded, a cancelled passphrase, or `user.signingkey` naming a missing file); no tag was created and nothing was pushed. Fix the signer and run it again.
   - exit 11: the previous release is not verifiably released — the check `release.yml`'s "Resolve the stack and the previous release" step runs (`signers.py previous`): its notes are on `main` but its `v<prev>` tag is missing, or that tag is lightweight, `gpg-unverifiable`, `no-anchor` or refused. Nothing was signed or pushed. Tag the earlier release first (`/release --tag <prev>`), or re-create its tag signed (or annotated with its fallback recorded), then run it again.

The next ship PR's `verify-release.sh` FAILs a lightweight tag, an unsigned one without the recorded fallback, one whose signature is BAD, one `signers.py` refuses (`unlisted`, `tagger-mismatch`, `revoked`, `revocation-unreadable`, `revocation-malformed`, `anchor-off-main` — an SSH-signed tag off `main`'s first-parent history —, `anchor-unverified`, `shallow`, `git-error`), or one off `main`.

Released docs are fixed at the tag: a released review, disposition, notes, migration or known-limitations file is never edited after its tag, except the schema-migration exception for security docs (`docs/security/README.md`) and the `/release` follow-up that records the annotated-tag fallback when it was created (the exit 4 stop path, merged before the tag is created; or the removal of a stale fallback line once a signed tag was created). The next ship PR's `verify-release.sh` reads the fallback line at the tag, or on `main` as it stood when the tag was created — a line added after tagging records nothing, so an annotated tag created without it must be re-created (signed, or annotated after the follow-up merges).
